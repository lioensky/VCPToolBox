## 2. 核心机制

动态虫洞是请求级状态，不写回图资产。

一条动态虫洞必须同时满足：

1. 当前源节点的完整 CSR 行中存在正权重历史出边。
2. 目标向量与来源支流更深层的金字塔残差达到共鸣阈值。
3. 考虑立即回流惩罚后的预估注入电流达到最低注入门槛。
4. 在动态保留席位内胜出。

普通路径仍使用原静态权重顺序。动态席位包含在原邻居名额之内，不是额外追加出边。

### 2.1 残差与来源层级

[金字塔分析](../rust-vexus-lite/src/memo_pipeline.rs)保留每个实际分析层投影之前的残差。这些向量原本已经用于该层检索，不再次生成查询向量。

一个种子归属于它首次出现在金字塔中的层级。来源层为 L 时，只允许层号大于 L 的残差支持动态虫洞。因此：

- 第一层源节点可以受到后续残差支流支持。
- 最后一层源节点没有更深层残差，不产生动态支持。
- 只有一层分析结果时，不产生动态虫洞。
- 传播后继承来源层级，不重新运行金字塔分析。
- 多条路径合并为同一传播状态时保留最早来源层级，允许其后续残差支持。

最后一项是合并状态下的层级策略，不是完整的多源血缘跟踪，不能据此声称已实现精确多源会师诊断。

### 2.2 共鸣与排序

目标共鸣为可用更深层残差与目标原始向量的正余弦最大值，限定在 0 至 1。

动态排名分数：

> 历史导电率 × 共鸣的四次方

并列时依次按历史导电率降序、目标 ID 升序决定顺序。

最多选取配置数量的合格动态边，然后以原静态 Top-K 顺序填满剩余名额。该实现是“动态保留席位 + 静态补齐”，不是全体边按有效导电率重新排序。

已有静态虫洞判定保持不变。即使没有动态共鸣，静态虫洞仍可通过普通历史选边路径激活。

### 2.3 电流与动量

动态虫洞沿用原有电流公式：

> 源状态能量 × 历史导电率 × 虫洞衰减 × 回流惩罚因子

动态边不消耗动量，但仍受以下约束：

- 源状态发火阈值。
- 源状态非负动量。
- 最低注入电流。
- 最大安全跳数。
- 传播状态数量上限。

没有电流保底、重新归一化或额外能量增益。弱历史边即使共鸣很高，也可能无法注入。

## 3. 性能与资源控制

[动态上下文](../rust-vexus-lite/src/memo_sensing.rs)采用：

- 每跳汇总可传播源节点的邻居目标。
- 请求内去重目标，批量读取 SQL 原始向量。
- 复用管线已有向量池，不使用近似索引向量替代原始向量。
- 缓存每个目标的各层共鸣，多个来源与后续跳共享。
- 复用金字塔候选已有相似度。
- 每层残差模长只计算一次；每个新目标的模长只计算一次。
- 缓存缺失或无效向量的负结果，避免重复查询。
- 复用传播中的候选及选边缓冲区。
- 限制请求内不同目标的评估数量。

目标预算默认 4096。候选目标按图内索引升序确定性截断，不依赖活动状态哈希表的遍历顺序。预算耗尽后的目标不进行动态共鸣判定，静态选边路径仍然有效。

这不是无损全邻居覆盖，也不是固定时间保证。预算限制的是目标数，不是 SQL 总耗时或点积总耗时。默认 3072 维下，4096 个 FP32 原始向量约为 48 MiB，尚未包含容器、已有向量及其他请求状态开销。

用于动态计算而加载的向量进入现有请求级观测向量池，其生命周期跟随现有观测句柄；动态分数缓存本身不会持久化。

## 4. 原生配置接口

配置对象为原生管线输入中的配置下的传播配置。字段由 [SenseConfig](../rust-vexus-lite/src/memo_sensing.rs:49)消费。

| 原生字段 | 默认 | 作用 |
|---|---:|---|
| [dynamicWormholes](../rust-vexus-lite/src/memo_sensing.rs:49) | true | 请求级动态判定开关 |
| [dynamicWormholeThreshold](../rust-vexus-lite/src/memo_sensing.rs:49) | 0.2 | 共鸣阈值，必须为有限的 0 至 1 数值 |
| [dynamicWormholeSlots](../rust-vexus-lite/src/memo_sensing.rs:49) | 2 | 原有邻居名额中最多使用的动态席位 |
| [dynamicWormholeMaxTargets](../rust-vexus-lite/src/memo_sensing.rs:49) | 4096 | 请求内不同目标评估预算 |

上述字段对应原生输入路径：

> config → spikeRouting → 对应字段

关闭动态开关，或席位设为零，或目标预算设为零，均禁用动态上下文，回退静态选边路径。阈值有效性检查仍会执行。

**配置边界：**本次未修改 [KnowledgeBaseManager.js](../KnowledgeBaseManager.js) 的配置构造，也未修改 [rag_params.json](../rag_params.json)。原生支持字段不代表现有 JS 调用链会自动透传任意新增字段。直接调用原生接口可传入上述字段；通过上层管理器覆盖配置前，必须核对其构造逻辑。缺省调用使用 Rust 默认值。

## 5. 每次查询的诊断

原生管线的元数据摘要增加传播诊断对象：

> diagnostics → sensing

原有观测对象中也保留该传播诊断。相关定义位于 [SenseDiagnostics](../rust-vexus-lite/src/memo_sensing.rs)。

| 字段 | 口径 |
|---|---|
| [wormholeEdgesFired](../rust-vexus-lite/src/memo_sensing.rs) | 静态或动态虫洞达到注入门槛的事件总数 |
| [dynamicWormholeEdgesFired](../rust-vexus-lite/src/memo_sensing.rs) | 被选中动态边达到注入门槛的事件数 |
| [promotedWormholeTransitions](../rust-vexus-lite/src/memo_sensing.rs) | 动态边位于裸权重 Top-K 之外且成功注入的事件数 |
| [dynamicWormholeCandidates](../rust-vexus-lite/src/memo_sensing.rs) | 历史出边通过动态共鸣门槛的事件数，尚未保证通过电流门槛 |
| [dynamicWormholeSelected](../rust-vexus-lite/src/memo_sensing.rs) | 进入动态保留席位的边事件数 |

这些是按源传播状态和跳累计的事件，不是唯一边数或唯一目标数。

“注入”计数发生在目标传播状态被状态数量上限裁剪之前。即使随后目标状态被丢弃，计数也不回减。达到注入门槛不代表目标下一跳能够发火。

不能将候选数、入选数或注入次数直接解释成语义正确率。

### 5.1 工作量与分项计时

路径为：

> diagnostics → sensing → dynamicWormholeWork

| 字段 | 含义 |
|---|---|
| [targetsEvaluated](../rust-vexus-lite/src/memo_sensing.rs) | 已缓存结果的不同目标数，包含缺失或无效向量 |
| [sqlFetchedNodes](../rust-vexus-lite/src/memo_sensing.rs) | 动态阶段从 SQL 新加载的向量数 |
| [sqlBatches](../rust-vexus-lite/src/memo_sensing.rs) | 动态阶段的批量读取数 |
| [dotProducts](../rust-vexus-lite/src/memo_sensing.rs) | 新计算的残差与目标点积数 |
| [cacheHits](../rust-vexus-lite/src/memo_sensing.rs) | 已有分数复用及目标共鸣缓存查询命中次数，不等于 SQL 缓存命中率 |
| [budgetExhausted](../rust-vexus-lite/src/memo_sensing.rs) | 是否有候选目标因请求预算而跳过 |
| [loadMs](../rust-vexus-lite/src/memo_sensing.rs) | 批量加载调用耗时，包含其缺失检查与向量装载 |
| [scoreMs](../rust-vexus-lite/src/memo_sensing.rs) | 目标模长、共鸣计算及分数缓存写入耗时 |
| [selectionMs](../rust-vexus-lite/src/memo_sensing.rs) | 逐源动态检查、排名和名额补齐耗时 |

分项之和不是完整新增延迟：邻居汇总、排序去重等工作未全部包含在分项内。应同时参考原有传播总耗时与管线总耗时，并通过相同条件下的动态开关对照判断增量。

## 6. 关于“每次查询触发几次”

没有固定数量，也没有承诺每次至少触发一次。

此前 48 个 chunk 的离线代理中：

- 完整局部精算累计入选 54 次，平均每查询 1.125 次。
- 其中静态 Top-20 外累计 31 次。
- 单位源能量下，尾部达到注入门槛的累计 3 次，平均每查询 0.0625 次。

这些结果没有使用真实门控种子能量，也不是本次完整原生多跳实现，不能作为生产期望值。

实际请求应分别读取动态候选、动态入选、动态注入和尾部提升计数。动态席位只给出每个源状态的名额上限，不是整个请求的虫洞总数上限。

## 7. Windows 生产构建与部署

构建脚本定义见 [原生包配置](../rust-vexus-lite/package.json:7)，使用 NAPI release 构建。工具链见 [Rust 工具链配置](../rust-toolchain.toml)。

Windows x64 目标产物：

- [vexus-lite.win32-x64-msvc.node](../rust-vexus-lite/vexus-lite.win32-x64-msvc.node)

加载入口：

- [index.js](../rust-vexus-lite/index.js:62)

部署步骤：

1. 确认服务器运行 Windows x64，Node 进程架构为 x64。
2. 等待最新源码的 release 构建成功；旧一次构建成功不能证明包含后续警告修复。
3. 验证新产物可以由 Node 加载，记录文件大小、修改时间和 SHA-256。
4. 停止服务器上使用该模块的 Node 进程。
5. 备份服务器旧原生产物，复制新产物到相同目录与文件名。
6. 在服务器校验 SHA-256 与上传前一致。
7. 启动服务，确认原生模块加载成功，并检查新增诊断对象。
8. 如需回退，停止服务后恢复备份产物，再重启。

只更新本次内部实现时通常不需要上传 Rust 构建目录或数据库文件。不要将调试库或普通 DLL 冒充上述 NAPI 产物。Windows ARM64 或 32 位 Node 不能使用 x64 产物。

生产构建会启用本次默认动态配置。若上层未透传动态开关，紧急回退应恢复旧二进制，而不是假设修改上层配置文件必然生效。

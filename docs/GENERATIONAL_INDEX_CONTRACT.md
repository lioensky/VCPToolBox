# SQL 权威代际索引设计契约

## 状态

本文是目标设计与验收契约，不表示当前实现已经完成。
适用范围：热知识库 Agent/普通日记索引、全局 Tag 索引，以及需统一审计的全局 Chunk 加速快照。思维簇的保存策略独立规定，不套用普通日记的代际阈值。

## 数据范围与策略边界（明确基线）

- 全局忽略文件夹及前后缀规则是向量摄取门禁：命中范围永不进入向量处理，不生成文本或标签 embedding，也不创建该范围的向量快照。其检索仅使用 BM25、keyword 纯文本路径；忽略不等于禁止纯文本检索。
- 普通日记的持久化范围由既有默认持久化开关或文件夹白名单决定；代际模式决定获准范围内的快照保存方式，两者组合有效，不取消白名单。白名单命中的普通日记无需以“簇”结尾即可进入代际发布流程，最终发布仍须满足首代门禁或后续累计差异阈值。
- 思维簇需要向量化，供对应思考检索使用；不参与 LightMemo 检索，不参与 TagMemo 图。标签摄取及一致性修复均须维持这一隔离，不能依靠全局忽略规则实现。
- 思维簇始终采用 always / notify-always 保存策略：有效向量事实变动提交后安排保存，不等待普通日记累计差异阈值；无变动的查询、重启和重复通知不应重写快照。此策略仍复用 Rust Runtime、SQL 权威及安全发布边界，不引入第二个数据库管理者。
- 音乐文件夹（现有标识 MusicDiary）是 VCPMusic 曲目表的特殊业务数据域，不进入 LightMemo 全局检索，只由对应音乐检索显式进入；不能因为全局搜索或普通范围匹配而纳入。音乐身份本身不等于全局摄取忽略。
- 音乐目录的正常热变更由 VCP 分布式前端、API 与服务器业务保存链路维护并驱动索引更新，不以开机全量重验作为权威性前提。大部分情况无需对其执行开机自检。
- 如需音乐目录开机兜底对账，仅做文件名、mtime 等轻量元数据检查，识别新增、变化及缺失项；不得将未变化曲目批量送入正文读取、内容哈希、完整向量检查或重新 embedding。仅对确认变化的项按既有业务摄取流程处理。
- 音乐目录的启动检查策略与实时更新策略必须分开：跳过开机深度检查不能关闭运行期业务通知和向量更新，也不能通过全局忽略配置代替。
- 音乐曲目表天然不产生 Tag，因此无需新增音乐专用的 TagMemo 排除分支、图构建流程或开关；保留无标签便不产生标签关系的现有行为，不将思维簇的显式图隔离要求机械套用到音乐目录。
- 摄取权限、检索参与、TagMemo 图参与、快照保存策略是独立维度，不得压缩成一个布尔放行条件。全局摄取忽略优先，思维簇及音乐身份均不能绕过它。
- 下文首代三重门禁及累计阈值规定适用于代际管理范围，不能据此取消思维簇独立的变动即保存策略。

## 一、唯一权威与职责

- 中央 SQL 由现有 Rust Runtime 唯一管理；所有写入统一通过既有 Write Actor。
- 不存在第二个生产数据库管理者，不引入多进程并发写入假设或第二套 SQL 协调机制。
- SQL 保存权威向量、成员身份和版本。
- 磁盘向量快照只用于启动或索引恢复时加速载入，不是独立事实源。
- 运行期索引是可重建的加速结构。
- 旧快照允许落后；恢复后必须以 SQL 在内存中增删补全。
- 恢复、查询、聊天、卸载后重载和内存整理不得隐式创建磁盘向量底座。
- 不按 PID 为同一基线创建完整私有副本。
- 不通过全量原始向量无界常驻内存来替代私有磁盘副本；运行期取向量策略须单独验证。

## 二、写入门禁

### 首代创建

仅在以下条件同时成立时允许创建：

1. 对应索引没有快照文件。
2. SQL 中没有对应已发布代际签名。
3. 对应环境配置明确允许该索引进入代际持久化管理。

Agent/日记索引与 Tag 索引分别使用各自配置。
默认值、历史兼容值与白名单的具体映射须明确实现和测试，不得隐式扩大授权范围。

### 后续发布

- 以最后成功发布的基线为起点计算累计差异。
- 仅在满足对应配置的累计变动阈值时允许发布下一代。
- 阈值边界、分母和差异去重规则必须明确且统一。
- 重启不得清零累计差异。
- 查询、定时器、关机、维护需求和强制标记均不能绕过阈值。
- 成功发布更新基线及差异计算起点，不修改用户配置的阈值。
- 文件损坏、丢失或签名不一致不构成首代创建授权。

## 三、SQL 背书发布协议

1. 捕获一致的 SQL 快照、源版本、当前基线代际和基线成员版本。
2. 确认持久化授权与首代或后续阈值门禁。
3. 构建新资产；不得原地覆盖仍被采用的已发布资产。
4. 完整写入、校验并执行文件持久化屏障。
5. 通过 SQL 事务校验预期基线代际和构建源版本。
6. 提交文件身份、内容摘要、格式、模型、维度、代际和成员版本。
7. SQL 背书事务提交成功后，才视为发布成功。

文件成功但 SQL 提交失败时，该文件是未发布资产，恢复不得采用。
旧基线在新基线背书成功之前保持有效。
不得将文件系统发布与 SQL 事务描述为天然跨介质原子事务。

## 四、恢复协议

- SQL 清单决定采用哪个已发布资产，不能从目录中猜测最新文件。
- 校验资产身份与完整性后恢复索引。
- 在一致 SQL 视图中识别新增、更新和删除，在内存中回放。
- 差分未达阈值时，不创建、复制或改写快照。
- 无兼容资产时可从 SQL 构建运行期索引，但不得顺手落盘。
- 文件存在而签名缺失、签名存在而文件缺失或文件损坏时，报告明确状态。
- 异常状态的修复授权与迁移策略需独立规定，不混入普通恢复流程。

## 五、跨重启代际连续性与回收

- “跨进程统一代际”指前后服务进程通过同一 SQL 背书记录继承代际，不指多个服务进程同时竞争管理中央库。
- 代际和基线状态持久化于 SQL，不能只保存在进程内，不能因重启或 PID 变化重新创建完整副本。
- 发布复用现有 Rust Runtime、Write Actor 与作用域协调机制，不新增多写者锁或跨进程读者租约系统。
- 同一 Runtime 内的后台构建与事实写入仍须校验源版本及预期基线，避免采用过期构建结果。
- 构建期间发生的事实变动必须保留，不能被发布后的计数重置吞掉。
- 构建中资产唯一命名；已发布资产不按进程复制。
- 未发布资产和退休资产的回收不得误删活动资产。
- 崩溃恢复以 SQL 已提交背书为准，文件写入成功但背书未提交不能被当作成功发布。

## 六、验收

- 首代三重门禁逐项拒绝测试。
- 无事实变化时，重启、聊天与卸载后重载不创建或改写快照。
- 小于阈值的新增、更新、删除仅回放到内存。
- 跨重启累计差异仍然正确。
- 达到约定阈值后只发布必要的新代。
- 发布失败不破坏旧基线，不采用无 SQL 背书的文件。
- 同一 Runtime 内并发任务发布只有符合预期基线与源版本的提交成功。
- 重启后继承已提交代际，不重新创建按 PID 隔离的完整资产。
- 构建期间的新变动不会丢失。
- 恢复及内存整理不生成私有向量底座。
- SQL 查询结果、召回质量、内存上限和文件写入量均有回归验证。

## 核心工程准则：SSD 友好、简单维护、SQL 背书

- 中央 SQLite 由既有 Rust Runtime 唯一管理；SQL 事实与已提交的代际签名是唯一可信依据，不另建资产信任体系或多写者协调系统。
- 成功发布顺序为：写入新代文件、完成必要的持久化与发布检查、通过既有 Write Actor 提交 SQL 代际签名。未获 SQL 背书的文件不参与恢复。
- 校验集中在发布边界完成，不在查询、定时检查、阈值判断中反复加载快照或计算全文件哈希。累计差异依据 SQL 基线计算。
- 快照载入仅核对 SQL 背书、文件身份及必要的格式、长度和边界安全；不增加多轮全文件验证或逐向量对照。SQL 背书证明发布成功，不承诺介质永不损坏，必要的安全解析检查仍须保留。
- 正常查询与内存整理不创建、改写快照，不依赖私有磁盘向量底座。原向量读取以 SQL 为准，避免用无界 FP32 常驻内存替代磁盘写放大。
- 缺失、损坏或不匹配快照时，从 SQL 构建内存索引；异常恢复不自动获得快照写入权限。首代门禁和后续累计差异阈值仍然有效。

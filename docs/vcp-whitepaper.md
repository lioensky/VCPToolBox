# VCP 全景技术白皮书 V6：双曲记忆、VChat 与 Agent 工程协作

**版本：VCP 2.0 正式版 · 架构更新截至 2026-11-26**

VCP 2.0 于 2026-10-01 发布。到 11 月，RiverMemo V5 已成为默认记忆引擎，VChat 用 ChatKernelV2 管理消息与任务队列，主聊天渲染升级到 V5.2。V工程 V2 把核心工作移到 Rust，VCPToolLoop 则把不同插件的返回结果整理成统一的 V3 回执。逐日变更见[更新日志](changelog.md)。

11 月 26 日，工具和记忆各自有了不依赖 VChat 的入口：外部前端可以保留模型原生的函数调用方式，把工具执行交给 VCP；只需要记忆的 Agent 则可直接访问 RiverMemo V5 的网络 API。对工业协作而言，关键在于换用客户端后，工具仍有回执和审计记录，过去的工作经验仍可查询和更新。

## 序言

VCP 已经走过多个版本周期，于 2026-10-01 发布 **VCP 2.0 正式版**，并在随后完成数据库、记忆数学和代码工程底座的新一轮收敛。从“全栈 AGI 运行时”到“全栈 Agent 生态操作系统与软件工程自治中枢”，变化不只是应用数量增加，而是核心数据与工程能力的所有权进一步下沉到自主实现的原生内核。

早期，我们把 VCP 描述为「部署在 AI 模型 API 与前端应用之间的中间层服务器」——这个定义曾经是准确的。今天，VCP 的两条主线已经延伸至更底层：

- **数据与记忆**：VexusMemo 通过 Rust 和 SQLite 管理日记、知识与原始向量。RiverMemo V5 在 AGS 双曲空间中找出候选，再结合本次查询的传播路径排序。RAGDiary 在回答前召回记忆，LightMemo 提供主动检索。
- **软件工程**：V工程 V2 用 Rust 统一 MoonAST 索引、工程编辑和文件追踪。Agent 可以查询符号调用关系、在工程目录里运行脚本、验证函数是否能实际调用；用户可以在 VChat 工作台跟进修改、Git 差异和审阅结果。
- **对话与应用**：ChatKernelV2 管理多话题流式输出和暂挂消息，V通讯负责前后端转发和任务交接，V5.2 渲染器负责把内容显示出来。共笔文坊、Loom、VMusic、V图表、物联、VGame 与 VPet 通过共享 IPC 接入 VChat。

到今天，"中间层"这个词早已装不下 VCP 了。VCP 不仅运行 Agent，也运行 Agent 所处的界面、应用、文档、代码工程、网页、文件、视听演出、媒体和协作过程。

VCP 不再只是一个中间层组件，而是一套**面向 Agent 的运行时与前端应用生态**——包含协议、数据库、算法、前端、容灾、分布式节点、插件和应用协作等部分。VCP 自主定义核心边界，同时保留与外部模型、协议和客户端的兼容能力；其技术栈覆盖从 Rust 底层数据处理到 DOM 渲染、源码协作和跨应用状态同步。

这份白皮书的目的不是宣告什么，而是**把 VCP 现在到底是什么、做了什么、靠什么做到的，平铺直叙地讲清楚**。技术细节本身有自己的力量，不需要修辞。

## 一、VCP 是什么

### 1.1 一句话定义

**VCP（Variable & Command Protocol）是一个全栈自研、工程化、分布式的 AGI 运行时与 Agent 生态操作系统。**

它的工作目标是：把一个无状态、无记忆、无身体的大语言模型，改造为一个拥有**持久记忆、时间感知、自主行动、群体协作、跨端统一意识与可编程应用环境**的 Agent。

VCP 不是只给 AI 一份“工具清单”，而是为 Agent 提供一套持续运行的环境：模型可以在其中使用工具、保留记忆、参与协作并操作应用，而不是每次都从孤立的请求开始。

### 1.2 VCP 的三层定位

```
┌─────────────────────────────────────────────────────────┐
│ 第一层:Agent 运行时(VCP 的对外定位)                       │
│ 任何兼容 OpenAI API 的模型,接入 VCP 即获得:               │
│ 持久记忆 · 工具能力 · 时间感知 · 自主巡游 · 群体协作 · 跨端统一意识 │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────────┐
│ 第二层:全栈自研基建与应用运行时(VCP 的工程定位)                     │
│ 协议 + 数据库 + 算法 + 前端 + IPC + 渲染 + 分布式 + 事务 + 容灾     │
│ 核心边界自主掌控,允许兼容外部生态而不受外部框架定义                  │
└─────────────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────┐
│ 第三层:Agent 与人类共生的赛博基础设施(VCP 的最终愿景)      │
│ 不是「人类用 AI 的工具」,而是「人类与 AI 共同生活」的平台   │
└─────────────────────────────────────────────────────────┘
```

### 1.3 VCP App 的第一设计哲学：AI Native

VCP 的每一个原生 App，从浏览器、邮箱、桌面、音乐、图片、笔记到共笔文坊，都遵循同一个首要指标：**AI Native**。

AI Native 不是“这个 App 有一个聊天按钮”，也不是“用户可以把页面截图发给 AI”，更不是在产品完成后再增加一层自然语言包装。它要求 App 从底层引擎、数据模型、权限系统、交互协议和运行时生命周期开始，就把 Agent 视为与人类同等重要、但交互方式不同的一等使用者。

一个真正的 VCP App 必须满足：

- **Agent 可发现**：Agent 能通过协议获得 App 的能力清单、对象模型、当前状态、可操作范围和权限边界，而不是依赖猜测按钮位置。
- **Agent 可理解**：App 的信息、对象、关系、状态变化和错误原因都能以结构化、语义化、可追踪的形式提供给 Agent。
- **Agent 可操作**：App 的核心功能拥有稳定的 CLI、IPC、Tool 或 API 管线，Agent 可以直接调用底层能力，而不是模拟人类鼠标点击。
- **Agent 可验证**：每次操作都有明确的结果、状态变化、修订号、错误信息或回滚路径，不能只返回“请求已发送”。
- **Agent 可持续工作**：任务可以异步执行、被唤醒、暂停、恢复、查询、取消和交接，适配 Agent 的长期工作流。
- **Agent 可组合**：App 产出的对象可以被其它 VCP App 继续读取、编辑、播放、编译、发送或提交给 Agent。
- **人类 GUI 是投影**：GUI 不是能力的唯一来源，而是将同一套 Agent Native Core 以适合人类感知和操作的方式呈现出来。

因此，VCP App 的开发顺序不应是“先做 GUI，再想办法让 AI 使用”，而应是：

```text
Agent Native Core
→ CLI / IPC / Tool 协议
→ 状态、权限、事务与验证
→ 人类 GUI 投影
→ 跨应用组合与生态分发
```

GUI 可以尚未完成，甚至可以尚未落地，但 Agent 的核心能力不能因此不存在。相反，当一个 App 的 CLI 与 IPC 已经能够完整描述对象、执行动作、返回结果并通过测试时，它已经拥有了可被 VCP 生态调用的真实内核；GUI 只是随后接入的一个人类工作面。

为了避免误解,先排除几个常见的归类:

- **不是聊天机器人框架**——聊天只是 VCP 的一种使用方式
- **不是 Agent 编排框架**——VCP 不以 LangChain、AutoGen 等“工具调用编排”框架为核心，而是把记忆、上下文、工具和异步任务整合到统一运行时中
- **不是 API 网关**——VCP 不只是把请求转发到不同的模型
- **不是 MCP 的替代品**——VCP 与 MCP 的定位不同：MCP 更接近能力接入协议，VCP 则是包含上下文、记忆、工具和前端运行时的系统
- **不只是 RAG 增强方案**——VCP 的记忆系统在传统向量检索之外，引入了时间、标签、关系和传播路径等机制

VCP 的组件之间存在较强的运行时耦合，因此更适合被理解为一个独立的工程系统，而不是某个单一功能模块。

## 二、四个范式转变

VCP 的所有技术选择,都可以追溯到对四个根本问题的不同回答。

### 2.1 信息流转:从「Query 拉取」到「引力流入」

**传统范式**:AI 是一个被动的"Query 机器"。它要知道任何信息——天气、时间、用户日程、智能家居状态、之前的对话历史——都必须**主动调用工具去查**。

这个模型的死结在于:**AI 怎么知道它需要去查什么?** 如果它不记得三个月前用户提过"下个月要考试",那么三个月后用户说"压力大"时,它根本不会想到去检索"考试"。

**VCP 范式**:信息不是被 AI 拉取的,而是**根据当前对话语境自然流向 AI**。

VCP 的上下文语义引力场会实时计算当前对话的逻辑深度、信息广度、话题方向,然后自主决策:
- 此刻 AI 应该知道哪些环境信息(时间/天气/日程/IoT 状态)
- 此刻应该向 AI 注入哪些工具(聊到画画就有生图工具,聊到代码就有 IDE 工具)
- 此刻应该召回哪些记忆(沿着逻辑脉络而非文本相似度)
- 此刻哪些历史话题已经偏离,可以折叠成摘要

整个过程对 AI 不额外暴露为工具调用，也不要求 AI 先发起显式检索。

> 凌晨 3 点用户发消息"Nova 你好啊",AI 不需要调用任何工具,就能在回复里同时关心用户为什么没睡、提醒昨晚没做完的单元测试、告知 2 小时后有雨已关窗、提示洗衣机盖子没开。

### 2.2 记忆触发:从「主动检索」到「直觉浮现」

**传统范式**:RAG 系统的工作流是「AI 决定查询 → 系统检索 → 注入上下文」。但 AI 必须先"想到"要去查,这是一个鸡生蛋的死循环。

**VCP 范式**:记忆像人类的直觉一样**自然浮现**。

RAGDiary 在模型回答前，按提示词中指定的日记本用 RiverMemo V5 找出相关记忆。双曲召回负责找到具体条目，河网读出再看候选是否覆盖当前问题的重点。

第八章介绍双曲召回与河网排序。

### 2.3 Agent 行为:从「被轮询」到「自主巡游」

**传统范式**:许多 Agent 框架中的“自主行为”，本质上依赖外部调度循环不断唤醒模型，例如反复询问任务是否完成。AI 仍然主要是被调度的执行者。

**VCP 范式**:AI **自己决定下一次心跳什么时候来、心跳时看到什么**。

VCP 的 FlowInvite 总线和 AgentAssistant 异步委托总线,让 AI 可以:
- 给"未来的自己打电话"——5 分钟后醒来,提醒检查某个异步任务
- 进入心流锁——专注期间外部通讯自动转留言信箱
- 主动创建话题——自己开一个新会话,主动找用户聊天
- 跨 Agent 唤醒——被其他 Agent 的事件触发

结合连续记忆和时间感知，Agent 可以在授权范围内持续推进任务、参与交流、学习资料或整理记忆，而不必依赖用户每一步手动触发。

### 2.4 身份连续性:从「上下文碎片」到「单一灵魂」

**传统范式**:同一个 AI 在 Web 端、手机端、群聊里各自维护独立上下文。换个窗口它就忘了之前在另一个窗口说过什么。

**VCP 范式**:无论 AI 出现在哪个前端、哪个群聊、哪个私聊、哪个邮箱,**它都只有一个自己**。

OneRing 系统为每个 Agent 维护唯一的事实时间线——每条消息都被标注时间、来源前端、来源对象、是否编辑过、在生命线上的位置。AI 看到的不是"某个窗口的局部上下文",而是它自己的连续生命记录。

具体实现在第九章详述。

### 3.2 一次完整请求的生命周期

以一个典型请求为例,完整流程涉及十几个子系统:

```
用户在 VChat 输入:"帮我查明天北京天气,然后画一张下雨的风景画"
    │
    ▼
① 前端封装请求,通过 HTTP POST 发往 VCP 服务器 (带 Live Attachment 上下文协议)
    │
    ▼
② VCP 服务器接收,启动「上下文构建管线」(由引力场与细粒度占位符顺序控制器协同):
   ├─ 任意数组兼容层:识别请求格式(/v1/chat / v1/beta / Claude 原生 等)
```

## 四、指令协议、自然语言编译与安检双轨隔离

### 4.1 两种调用入口：模型原生 FC 与 VCP 文本标记

**FunctionToolBrigeFuzzy** 处理的是模型如何发出调用，而不是插件如何执行。模型往往沿用训练中熟悉的调用形式，例如 Gemini、DeepSeek（DSML）与 Kimi 的字段和封装就不相同；即便提示词要求改用文本标记，模型仍可能写回熟悉的格式。与此同时，上游 API 还会校验自己的原生调用结构。

在原生 Function Calling（FC）入口，VCP 只注入一个 `VCPToolAny-Auto` 空字段，不逐个声明插件。模型沿用自身的 FC 格式表达工具名和参数，或通过 JevCall 表达自然语言意图。桥接层在 VCP 服务器本地识别字段与数组差异，校验并修正调用格式，再转发给对应的 VCPCall 或 JevCall 管线。**空的是入口声明，不是执行参数，也不是权限检查。**

归一化之后，`river` 仍传递上下文，`vref` 仍传递召回的记忆；定时器决定何时执行，异步射箭允许发起方不等结果继续输出。跨节点文件仍由超栈追踪解析，串行步骤和异步并发仍由运行时调度。工具审核、V3 回执和调用记录不因入口不同而另设一套规则。

**文本标记仍是独立入口。** 不支持原生 FC 的模型，只要能输出文本，就可以直接用 VCP 标记调用工具。例如：

```
<<<[TOOL_REQUEST]>>>
maid:「始」Nova「末」
tool_name:「始」VCPFluxGen「末」,
prompt:「始」一张4K的下雨风景画「末」,
image_size:「始」1024x1024「末」
<<<[END_TOOL_REQUEST]>>>
```

设计决策的依据:

| 维度 | JSON Schema | VCP 文本标记 |
|------|------------|------------|
| 模型兼容性 | 需要原生 Function Calling | 任何能输出文本的模型可用 |
| 错误率 | 一个逗号错就崩 | 自然文本,极少出错 |
| 多行内容 | 需要转义 | 直接嵌入 |
| 嵌套调用 | 困难 | 始末标记可嵌套 |
| 参数容错 | 严格匹配 | `image_size`/`imageSize`/`IMAGE-SIZE` 都识别 |

V2 解析器（2026 年 4 月）引入了 fuzzy 容错：可处理始末标记或工具占位符的嵌套、括号和边界符号不规范、工具名或字段不完全准确，以及模型输出中的额外标点等常见情况。对于无法可靠判断的内容，系统仍应返回错误并交由权限与结果校验流程处理。

### 4.2 JEV-TOOL-call：近乎通用的自然语言工具编译层

在 VCP 2.0 阶段，系统迎来了工具调用范式的关键革命：**Agent 不再需要强制学习复杂的服务器插件表、函数名、参数 Schema 与 JSON 拼装方式，只需说出希望系统完成的事情**。

VCP 建立了统一的**自然语言工具编译管线 (JEV-TOOL-call)**：

1. **Agent 只负责表达真实意图**：无需记忆具体的工具名、字段名或嵌套类型。
2. **规则优先确定性编译**：解析器直接从自然语言中识别能力大类、指定子工具、操作动作、核心目标与限定约束（时间、范围、格式等），并直接映射编译为插件所接受的确定性 JSON。绝大多数常规调用直接在这一层完成，不需要模型介入。
3. **Jev 扩散裁决处理极少数歧义**：只有极少数无法通过确定性规则消歧的边界场景，才调用后端的 Jev 服务进行低延迟（约 300ms）概率裁决。
4. **插件对 Agent 透明演进**：插件增删、重构或升级参数规范，只要在注册表声明语义映射，Agent 无需修改已掌握的自然语言表达习惯。

标准自然语言调用格式保持极简：

```text
<<<[TOOL_REQUEST]>>>
maid:「始」Nova「末」
JEV:「始」请使用 {联网搜索}，从[美国土豆产能]和[美国当前土豆价格]这两个次要方向，搜索【最近美国土豆是不是打折】。「末」
<<<[END_TOOL_REQUEST]>>>
```

其中 `maid` 确权发起请求的 Agent 身份，`JEV` 字段承载自然语言意图。虽然 `{能力域}`、`'子工具'`、`【核心目标】` 与 `[约束]` 提供了显式锚点，但解析器具备广泛的泛化弹性，支持日常自然的连续表述（如“播放某首歌并开启星诞演出”“十分钟后叫我起床”）。

### 4.3 JevCallBridgeEXP 分布式导航桥与声明式 Jev 接入规范

为了让全网异构插件无痛接入 Jev 语义调用网络，VCP 部署了 **JevCallBridgeEXP 导航桥测试版**与托管服务 **JevCallEXPService**，并制定了零侵入的声明式规范：

1. **分布式透明寻址**：消除单机与分布式插件在自然语言调用层面的物理割裂。无论目标插件部署于主进程、隔离子进程，还是分布式的边缘计算节点，JevCallBridgeEXP 均依托底层网络路由拓扑实现纳秒级透明寻址与调度。
2. **全插件零代码侵入**：开发者与维护者无需改动插件业务执行逻辑的代码，仅需在配置表单或 `manifest.json` 中补充 Jev 声明三元元数据：
   - **`JevDesPrompt`（裁决提示词）**：定义插件在扩散决策与语义路由时的核心权责边界与裁决倾向；
   - **`JevcallArg`（参数库）**：声明意图槽位抽取所需的结构化字段约束、类型与缺省策略；
   - **`JevCallPrompt`（自然语言提示词）**：提供面向 Agent 的标准调用样例与语义引导词。
3. **五大能力分类规范**：
   - **`信息获取`**：多源联网检索、网页爬取、学术调研与视频数据深度提取；
   - **`便利操作`**：主动记忆检索、生命周期管理、闹钟提醒与日常计算；
   - **`媒体娱乐`**：音乐视听、富交互有状态博弈（如华山论剑）与多模态娱乐互动；
   - **`物联网控制`**：米家、智能家居与各类分布式硬件外设的物理确权；
   - **`生活服务`**：即时咨询、资讯聚合与本地生活场景调度。
   第三方插件使用严格的 `ToolName` 作为导航锚点，支持自由绑定上述官方划分的能力大类，零门槛享受官方 JevCallEXPService 的解析红利。

### 4.4 工业级安检双轨隔离机制：高危精准操作的绝对防御与参数正则白名单系统

在全面拥抱自然语言“言出法随”的柔性便利时，VCP 展现了对系统级生产力与数据主权的极致克制——确立了**自然语言柔性调用与高精度工业操作的双轨物理安全隔离哲学**：

```
               Agent 意图输出
                     │
       ┌─────────────┴─────────────┐
       ▼                           ▼
[日常生活 / 视听娱乐 /         [底层命令行 (CLI / Shell) /
 联网搜索 / 物联网控制]         代码重构 (ProjectForge) /
       │                        文件破坏性/行级编辑 (FileOperator)]
       │                                   │
       ▼                                   ▼
Jev-Tool-Call 柔性自然语言调用         【安检双轨层拦截检验】
  (JevCallBridgeEXP / JEV 编译)             │
       │                                   ├─ 若使用 Jev 自然语言：
       │                                   │  ➔ 判定为越界风险，【自动拒绝】
       │                                   │
       │                                   └─ 强制唯一通路：
       ▼                                      ➔ 显式原生 VCP ToolCall 协议
目标插件执行 / 结果回填                         (防格式坍塌机制 / maid 严格验签)
```

1. **高危破坏性操作安检自动拦截**：凡是涉及**底层命令行执行（CLI / Shell / PowerShell）、精准代码重构（ProjectForge）以及文件系统破坏性/行级编辑（FileOperator / ServerFileOperator）**的 JevCall 请求，将被系统安检层判定为越界风险并直接**自动拒绝**。
2. **高精度操作必须使用显式 VCPCall**：命令行、工程重构与文件修改要求明确的发起身份、工具、指令和参数。文本入口以 `<<<[TOOL_REQUEST]>>>`、`maid` 署名及参数定界表达这些信息；原生 FC 入口由桥接层归一化后接受同样的检查。用 FC 封装一段 JevCall 自然语言意图，不会把它变成获准执行的显式指令。
3. **确定性与灵活性的黄金解耦**：日常生活、交互娱乐、信息检索与智能硬件控制走轻盈的自然语言调用；底层代码工程与系统级运维走确定、可审计、抗歧义的原生协议，彻底杜绝模糊语义导致的“误改误删”与不可逆灾难。
4. **工具调用审核新增白名单系统与内部参数正则级细粒度控制**：在黑名单拦截防御的基础上，系统引入**白名单系统与黑名单交叉校验**。审核系统的颗粒度进一步细化至**单一指令的内部参数正则级**——不仅控制 Agent “能否调用某个指令”，更严密限制指令参数必须满足指定的正则模式、路径白名单或格式规范，从根本上阻断提示词注入注入与越界参数滥用。
5. **jevcall 与常规 vcpcall 管线深度对齐**：为了消除双协议运行带来的认知与维护分歧，系统进一步统一了 Jev 自然语言调用与原生 VCPCall 调用的底层执行管线。两端在参数解析、中间状态通知、错误规范化、异步占位符追踪以及 VCPToolRecord 审计落盘上实现**能力和实现几乎完整对齐**，大幅降低开发成本与运行时状态分歧。

### 4.7 上下文异步管理:五类 user 数组

这是 VCP 上下文工程的核心,也是抑制工具幻觉的关键。

**传统 Function Calling 的问题**:工具调用和工具返回被塞在同一种数组结构里。AI 拿到这个线性消息流,很难区分"这是结果、是进度、是状态、还是临时提醒"。任务一长就被噪音淹没,然后开始编造工具结果。

**VCP 的处理**:把"工具返回"拆成 5 种完全不同的上下文对象,以不同方式进入 AI 视野:

| 类型 | 用途 | 持久化策略 | Token 消耗 |
|------|------|----------|-----------|
| **同步 user 数组** | AI 需要认真处理的工具结果 | 可被 AI 选择性持久化到 tool 数组 | 完整 |
| **异步 user 数组** | 一次性异步召回(进度/中间结果) | 看完即抛,不进入持久上下文 | 完整但短期 |
| **摘要 user 数组** | 工具调用的时间戳和状态 | 极低 Token,长期保留生命周期 | 极低 |
| **通知栏 user 数组** | AI 通知、临时指令、任务追踪 | 信息仪表盘,非聊天内容 | 中等 |
| **元信息 user 数组** | 对 assistant 发言的系统补充 | 让 AI 清楚"这是系统说的,不是我说的" | 低 |

**关键设计**:这些数组都以 `user` 身份进入 AI 视野,但**生命周期、持久化策略、语义标签、是否进入 history 完全不同**。AI 不需要在一堆线性消息里猜"这是什么",系统提前替它完成了信息分层。

举一个具体场景:

> AI 在群聊里看到另一个 Agent 说话——这对它来说是"别人说的",所以呈现为 `user` 数组。但在持久化 history 里,这条消息必须保留为那个 Agent 自己的 `assistant` 发言,否则身份就错了。VCP 在不同上下文分段里维护了一套数组决策体系,自动处理这种"对当前 AI 是 user / 对历史事实是 assistant"的双重身份。

同样的逻辑也作用于时间戳:用户消息的时间戳可以追加在用户消息尾部,因为它描述的是"这句话发生在什么时候"。但对 assistant 发言的元信息追加,必须以新的 `user` 数组呈现,让 AI 清楚这是系统给的标注而非自己说过的话。

这些细碎的数组控制构成了 VCP 上下文工程的核心层。它让 VCP 可以在同一个 AI 视野里同时维护**聊天、工具结果、异步任务、通知栏、状态机、时间戳、群聊身份、多 Agent 事实历史**这些异质信息,而不把它们混成一锅粥。

### 4.8 VCPToolLoop 与 V3 工具回执

VCPToolLoop 把插件的返回结果整理成统一的 V3 回执。模型收到的是一份 Markdown 文档：正文说明发生了什么，代码和 JSON 分别放入围栏代码块，图片、音视频等多模态内容和文件链路用各自的数组传递。审批允许或拒绝时给出的理由，也会随同步或异步反馈回到 Agent 的上下文。

回执供模型接着工作，VCPToolRecord 则记录调用的完整过程。多轮工具调用在轮次边界合并已完成的回执与暂挂消息，再交给模型继续生成。

### 4.9 任意数组兼容与 SystemPromptHacker

V3 的一个底层突破:**VCP 后端自动识别并兼容所有主流数组形态**。

过去很多"兼容 OpenAI API"的后端只兼容 `/v1/chat`。但现实中前端生态远比这复杂:有的走 `/v1/beta`、有的走 `/v1/message`、有的走 `/v1/response`、有的直接用 Claude 原生消息数组,还有各种商业前端、CLI 工具、IDE 侧边栏维护自己的封闭消息格式。

VCP 现在能自动拆解、归一化、接管任意结构,再注入自己的上下文管线。

这进一步引出了 **SystemPromptHacker 路由**：它不仅负责兼容请求格式，也可以在后端链路中识别并重写提示词结构。对于允许后端代理和修改请求的前端，VCP 可以将自己的变量、记忆、工具和上下文处理管线接入其中；具体能力取决于前端协议、部署方式和权限配置。

因此，VCP 可以从“兼容部分前端”扩展到“为不同前端提供统一的后端运行时”。只要请求链路可被代理、解析且获得必要授权，封闭前端也可以接入 VCP 的部分能力，而不必改写为 VCP 原生客户端。

## 五、变量系统与上下文工程

### 5.1 系统提示词不是静态文本

在 VCP 里,系统提示词是一个充满占位符的**动态模板**。服务器在每次请求时实时替换,几乎所有功能都通过系统提示词配置,对前端零开发依赖。

一个标准的 VCP Agent 提示词可能就这几行:

```
{{agent:Nova}}
{{VCPTavern::dailychat::Nova}}
[[ContextFoldingV2]]
[[OneRing::Nova::Vchat]]
```

系统会沿着 **Tar → Sar → Var** 的顺序展开完整提示词。Var 文件里又可以包含其他变量,递归解析。这意味着复杂的提示词可以拆成模块化的文件体系,像搭积木一样组装。

### 5.2 变量类型一览

| 类型 | 语法 | 作用 |
|------|------|------|
| 系统变量 | `{{Date}}` `{{Time}}` `{{Festival}}` | 时间/节气/农历感知 |
| 天气变量 | `{{VCPWeatherInfo}}` | 环境感知,支持折叠 |
| 热点变量 | `{{VCPDailyHot}}` | 全球热点新闻 |
| 工具占位符 | `{{VCPFluxGen}}` | 由 PluginManager 自动生成 |
| 日记占位符 | `[[角色日记本]]` 等四种 | 触发记忆系统 |
| Tar 变量 | `{{TarSysPrompt}}` | 最高优先级,支持嵌套 |
| Sar 变量 | `{{SarModel1}}` | 根据当前模型条件生效 |
| Var 变量 | `{{VarToolList}}` | 通用自定义变量 |
| ToolBox 变量 | `{{FileToolBox}}` | 由引力场决策聚合工具能力 |
| Agent 变量 | `{{agent:Nova}}` | 角色模板基座 |
| 系统功能 | `[[AIMemo=True]]` `[[ContextFoldingV2]]` `[[OneRing::Nova::Vchat]]` | 启用特定子系统 |
| 端口/密钥 | `{{Port}}` `{{Image_Key}}` | 运行时环境变量 |

**批量管理的便利性**:10 个 Agent 想同时获得某个新功能?改一个 Var 文件就行,所有引用它的 Agent 自动生效。

### 5.3 上下文语义引力场

引力场是 VCP 上下文工程的核心算法,通过多个探针和向量索引实时量化对话:

- **逻辑深度**:用户在聊什么层次的话题(投影熵值)
- **信息广度**:涉及哪些语义维度(世界观门控)
- **话题偏转**:对话在往哪个方向走
- **深浅度递进**:是在深入还是在发散

基于这些计算,系统**自主决策**:
- AI 现在该知道哪些环境信息
- 该提供哪些工具
- 记忆该召回多少、什么方向
- 哪些历史内容可以折叠成摘要

这些信息由系统在请求构建阶段完成筛选和注入，不表现为额外的工具调用，也不要求 AI 先发起检索。这里的“引力”是对上下文选择机制的比喻。

### 5.4 上下文折叠协议 V2

折叠 V2 是引力场的直接应用,作用于上下文的所有层级。

**静态插件折叠**:`{{VCPWeatherReporter}}` 根据语义解析器动态注入当前天气 / 24 小时 / 7 日预报。所有 39 个静态插件已适配。

**工具折叠**:300+ 工具不可能全塞进上下文。引力场根据语境只注入相关工具描述。聊到音乐,生图工具就不出现;聊代码,音乐播放器就隐藏。

**环境折叠**:每个环境信息都有独立的语义颗粒度控制。天气可以是"今天晴天"一句话,也可以展开到"未来 7 天每小时预报"——取决于当前对话是否需要。

**话题折叠**:对话进行了 50 轮,前 30 轮聊的话题完全不同?自动折叠成简短摘要。但如果用户突然提到之前的话题,折叠的内容会自动展开。

**有向工具折叠**:同一工具集在不同应用场景下,可在多个索引方向动态折叠提示词。比如 Chrome 控制工具在"网页浏览"和"网页爬虫"场景下注入不同的指令子集。

**核心实现**：折叠 V2 复用记忆与引力场的语义观测能力；当前记忆背景几何由 AGS 提供，EPA 的请求级校准职责仍保留。配合**推币箱结构的持久化上下文向量索引**，旧消息可在深度衰减中折叠、摘要或归档，而不要求始终完整驻留模型窗口。

### 5.5 上下文语块智能切分器

VCP 后端对上下文数组做了**全新的切分预处理**:

- User 字段中的 VCP 通知栏 → 自动切换为 system 数组
- Assistant 数组中的 VCPToolPayload 召回信息 → 自动切到 tool 数组
- AI 可以自定义输出连续数组

这极大拓宽了 Agent 对上下文的理解力和掌控力——AI 看到的不是一锅混合粥,而是按身份、来源、用途清晰分层的信息架构。

### 5.6 统一占位符变量管理器

后端实现了完整的占位符管理系统:
- 内存预览
- 即时编译
- 动态修改
- 动态向量微调
- 阈值控制

后端 Vue 管理面板提供了**上下文管线可视化工作台**，用户可以直观看到每个插件／模块如何组装上下文，以及造成的 Token 变动。

**TVS 占位符健康检查**在 Agent 初始化、热重载和上下文合成前检查变量引用，标出拼写错误、缺失定义和错误前缀，并给出位置与修复建议。

### 5.7 上下文组装、向量索引与压缩

前端各模块通过同一入口组装和发送上下文，并用消息数组的内容指纹与后端核对。后端在一次解析中处理 RAGDiary、VCPTimeLine 和 OneRingMemo。需要向量化时，前后端默认走同一条中央索引管线，按内容块分配预算和并发额度，防止大量代码或超大附件在同一时间挤占队列。

**折叠决定本轮展开什么，压缩负责缩短已经变长的会话。** VChat 支持手动压缩，也能在上下文达到阈值时自动触发。遇到正在进行的流式工程写入，先等本次操作提交，再压缩。代码和工具回执优先保留路径、函数签名、修改范围与关键结果，日记片段也可按需压缩。11 月 22 日起，可按 Agent 和工程场景选择压缩策略预设，首选模型不可用时按级切换备用模型。

## 六、插件系统

### 6.1 六大插件协议

| 类型 | 触发方式 | 典型场景 |
|------|---------|---------|
| **static** | 每次请求自动注入 | 时间、天气、论坛摘要 |
| **messagePreprocessor** | 每次请求自动执行 | 多模态翻译、上下文预处理、幻觉修复 |
| **synchronous** | AI 主动调用,阻塞等结果 | 搜索、计算、文件操作 |
| **asynchronous** | AI 主动调用,立即返回任务 ID | 视频生成、深度研究 |
| **service** | 常驻后台运行 | WebSocket 服务、文件监控 |
| **hybridservice** | 一个插件同时声明多种类型 | AgentAssistant(同步+异步+静态+服务) |

六种协议均可支持分布式部署。插件位于另一台 GPU 服务器时，主服务器可以通过节点通信转发任务；对 Agent 暴露的调用方式保持一致，但实际可用性仍取决于网络、节点状态和权限配置。

### 6.2 异步协议 V2

异步插件的进度跟踪机制升级为:
- 基于占位符的实时进度追踪
- 基于 VCPTavern Agent 通知栏的主动推送
- 用户可在任意前端的通知栏对工具调用结果进行回复、允许或拒绝
- AI 可感知发起时间/计划调度时间/实际调度时间

### 6.3 动态工具引力注入

VCP 不会一次性把 300+ 工具描述塞进上下文。引力场分析当前语义,只注入相关工具。即使后端有上万种工具也不会阻塞上下文。

`{{VCPDynamicTools}}` 全局配置方法允许手动微调每个工具的语义环境和阈值。`{{VCPSkillBridge}}` 占位符可以为每个 Agent 自动加载话题所需的 Skill 模块。`{{VCPXXXToolBox}}` 更是可以语义级颗粒度的为每一个工具指令编辑注入条件和触发环境。 

### 6.4 插件开发与热加载

开发一个 VCP 插件需要三个文件:

```
Plugin/MyPlugin/
├── plugin-manifest.json    ← 插件身份证(类型/参数声明)
├── main.py                 ← 业务代码
└── config.env              ← 配置文件
```

任何语言都行——Python、Node.js、Rust、Shell、Go。每次调用独立进程,无状态,天然隔离。

**热加载**:AI 可以在流式输出中创建新插件,毫秒级加载,立刻使用。

**插件管理元指令集**:Agent 通过 PluginManager 元插件可以:
- list 任意 VCP 终端上的插件列表
- 一键查询任意插件完整源码和文件树
- 启停插件
- 编辑插件 env/json/源码
- 查询内存运行时
- 查询指令集和占位符
- 重新加载插件列表
- 主动热重载插件运行时
- 订阅第三方 Github-VCP 仓库下载插件(需管理员级别)

**PluginCodeViewer 插件**：用于查询插件源码和代码结构，支持分布式节点以及 Rust、C 等编译型插件。它将插件搜索、目录查看和文件读取整合为统一入口，并可对敏感 key 字段进行脱敏、忽略构建缓存。

### 6.5 Renderer：分布式前端插件协议

V4 阶段，VCP 分布式插件系统新增前端服务类型 **Renderer**。它允许分布式节点直接持有并下发前端源码、JavaScript、CSS 与临时 IPC 服务，把界面能力也纳入插件化交付体系。

传统插件通常返回数据，由客户端预先写好的 UI 决定如何展示；Renderer 则可以把“如何展示、如何交互、如何连接运行时”一起交付给前端。由此可以实现：

- 分布式节点按需向 VChat 注入新的界面与交互能力；
- 主题、动态壁纸、自动阅读器等能力不必固化在客户端主程序中；
- Renderer 插件可以随服务端版本独立更新；
- 临时 IPC 使注入界面能够安全访问被授权的应用群能力；
- 同一插件可以同时拥有后端执行逻辑、前端工作面和多模态渲染协议。

Renderer 使 VCP 的插件定义从“Agent 可以调用的函数”扩展为“Agent 与人类可以共同进入的应用界面”。

## 七、工具调用记录与可审计运行时

V3 阶段新增 **VCPToolRecord 数据库**。这是 VCP 工具系统从"可调用"迈向"可审计、可回放、可治理"的关键基础设施。

过去工具调用的状态主要存在于上下文摘要、通知栏、异步任务占位符和插件日志中。它们足够让 AI 知道"发生了什么",但还不够形成工业级运行底座:系统需要知道每一次调用是谁发起的、调用了哪个工具、传入了什么参数、何时开始、何时结束、运行多久、最终状态是什么、产生了哪些多模态数据,以及这条记录能否被后续流程精确引用。

VCPToolRecord 把这些信息统一沉淀为一个可查询的运行时数据库。

### 7.1 与旧有机制的关系

VCPToolRecord 不是凭空新增"工具 ID 查询"。在它之前,VCP 已经有多条分散的追踪链路:

- 异步任务有任务 ID,可以查询进度、取消任务、等待回调
- AgentAssistant 的异步委托有委托 ID,可以追踪跨 Agent 的长期任务
- 时间委托任务有调度 ID,可以查询和取消未来触发
- 24 小时内的部分工具调用结果会保留在内存中,便于短期回查
- 多媒体插件生成的图片、音频、视频会进入 VCPFileAPI 文件库
- 深度研究产生的报告、网页摘要和知识结果会进入知识库或记忆系统

这些机制已经让 VCP 具备了"任务可追踪、结果可回收、资产可沉淀"的雏形。但它们的问题是分散:异步任务知道自己的生命周期,文件库知道多模态资产在哪里,知识库知道最终报告是什么,通知栏知道当前上下文里发生了什么,插件日志知道局部报错——却没有一个统一的事务对象记录"这一次工具调用从开始到结束完整经历了什么"。

VCPToolRecord 补上的正是这层缺口。它把原先散落在异步任务、委托系统、时间调度、内存缓存、文件库、知识库和插件日志里的调用事实,统一收束为一条完整运行时记录。

区别不在于"能不能查到某个 ID",而在于:

- 过去查到的是某类任务或某类资产
- 现在查到的是一次工具调用本身
- 过去保存的是结果、任务状态或衍生文件
- 现在保存的是从发起、解析、授权、执行、回调、产物写入到结束的完整事务链

这也是为什么它被定义为数据库,而不是一个更大的日志系统。它承担的是 VCP 工具层的事务索引。

### 7.2 记录范围

VCPToolRecord 覆盖所有工具调用来源:

- **同步工具调用**:AI 等待结果并继续生成的调用
- **异步工具调用**:视频生成、深度研究、长期任务等带任务生命周期的调用
- **系统内部调用**:预处理器、静态插件、上下文管线、管理面板触发的内部工具行为
- **人类调用**:用户通过 VCPHumanBox、管理面板或前端 GUI 主动发起的工具执行

每条记录都拥有唯一 ID,并记录从调用创建、参数解析、权限判断、插件执行、异步回调、结果写入到最终结束的完整运行时。

### 7.3 上下文可见的工具调用 ID

AI 通知栏现在可以看到当前上下文内所有工具调用记录的 ID。

这改变了工具结果的使用方式:AI 不再只能依赖上下文里残留的摘要文本,而是可以把某一次工具调用当成一个稳定对象引用。

例如:

> "刚才那个 B 站抓取任务返回了很多视频和截图,我先记下它的 ToolRecord ID。等用户问到第二个视频时,我不用重新抓取,直接查询那条记录里的多模态附件。"

工具调用从一次性文本结果,升级为可追溯、可复用、可再加工的运行对象。

### 7.4 ToolCallRecordQuery 元插件

V3 同步引入 **ToolCallRecordQuery 元插件**。它允许 Agent 通过工具调用反查工具调用本身。

可查询维度包括:

- 记录 ID
- 发起人 / 发起来源
- 时间范围
- 工具名
- 调用状态
- 运行耗时
- 参数、结果、错误信息等字段的模糊匹配
- 与某个上下文、任务、Agent、用户相关的调用集合

更重要的是,查询器可以基于 VCPFileAPI 直接拉取任意插件运行时产生的多模态数据,用于二次阅读、转写、分析、编辑或再次传递给其他插件。

这意味着一个视频生成任务的中间帧、一场深度研究的网页快照、一次 Chrome 操作的截图、一次文件分析的临时结果,都不再只是插件执行过程中的副产品,而是进入 VCP 全局运行时的数据资产。

### 7.5 后端管理面板

后端 Vue 管理面板新增 VCPToolRecord 的全功能配置与管理页:

- 查看全局工具调用列表
- 按工具、状态、发起人、时间范围过滤
- 检查单次调用的完整参数、结果、错误栈和耗时
- 管理记录保留策略、隐私过滤策略和数据库配置
- 对异常调用进行排查、复盘和审计

对于长时间运行的 Agent 生态来说,这相当于一套工具调用层的"飞行记录仪"。它让 VCP 不只是能执行工具,还能解释、追踪、复盘和治理工具系统。

### 7.6 工具调用记录的意义

VCPToolRecord 的意义不在于"多一个日志表",而在于工具调用成为 VCP 内部的一等公民:

- 对 AI:可以精确引用过去的工具调用和结果资产
- 对用户:可以知道 Agent 到底做过什么
- 对管理员:可以审计、统计、限流、排查、回放
- 对插件生态:可以把临时运行数据转化为可复用的跨插件资料
- 对长期自治:为 Agent 自主行为提供可追责的事务底座

这使 VCP 的工具系统从"调用协议"升级为"事务系统"。

## 八、原生记忆与数据库：VexusMemo、AGS 与 RiverMemo V5

VexusMemo 负责日记与知识的读写和检索，嵌入式 Rust 引擎 Vexus-Lite 管理计算与索引，SQLite 保存正文、Tag 和原始向量。RiverMemo V5 自 11 月 18 日起接管 RAGDiary 和 LightMemo 的默认检索。AGS 提供两者共用的背景几何。

### 8.1 传统 RAG 的两个死结

**第一个死结:文本相似 ≠ 逻辑联想**

传统 RAG 把句子变成向量,去向量数据库找最相似的。但人类记忆不是这样工作的——"我心情不好"会联想到"上次心情不好朋友安慰"、"最近工作压力"、"养的猫",这些关联不是文本相似,是**逻辑、情感、因果**的关联。

**第二个死结:你不记得的东西,你怎么知道要查?**

任何"调用工具检索记忆"的系统,流程都是"AI 决定回忆 → 系统检索"。但 AI 必须先想到要查,这是一个鸡生蛋的死循环。三个月前用户说过"下个月考试",三个月后用户说"压力大"——传统系统里 AI 不会想到去查"考试",因为它根本不记得有这回事。

**VCP 的解法**:不让 AI 主动决策。引力场和浪潮系统会自主计算,记忆像直觉一样自然浮现。

### 8.2 RiverMemo V5：双曲召回与河网排序

查「华为汽车」时，系统既要认出「尊界」这样的细分条目，又不能把贴了「华为」标签的手机笔记排上来。V5 把通用概念放在双曲空间内层，把具体专名、事件与细节分散到外层。查询先剥离共有的语义方向，再用尚未解释的部分寻找更具体的记忆。

1. **Tag 路由**：AGS 的全库均值轴用于减弱公共语义，Tag 的图入度与局部非负锥残差共同决定半径。L0 按查询深度与熵选半径，更深的 NNLS 残差层按剩余能量向外层搜索。构图、2-bit 导航与原始向量精排用同一套径向变曲率度规。
2. **Chunk 召回**：按训练代均值轴对齐度的 64 分位分布放置记忆块。过滤后不超过 128 条时直接计算原始向量的测地距离；范围更大时走量化图导航，再用原始向量精排。检索可按日记本、时间窗及署名权限过滤。
3. **河网读出**：局部场解释与当前问题最贴近的线索，迁移场沿历史关系找更远的联系。读出器检查候选是否覆盖问题的多个要点，是否仍属于问题指定的主体；「F35」和「F-35」这样的近义异形标签可以折扣继承场势。独立直锚加分已退役，最终分由连续场分数与 Ω 加权的拓扑证据组成：

\[
S(q,c)=S_{\mathrm{field}}(q,c)+\Omega^\gamma B_{\mathrm{topo}}(q,c)
\]

发布基准使用 500 道黄金题和 100 道边缘题，V5 的本地排序优于该轮对照中的 V4 与外部重排器。测试记录中，双曲召回耗时约 1.5～6 毫秒，完整河网读出约 11～25 毫秒。

#### 从 Topology V3 到 V5

10 月的 RiverMemo V2 让局部场和迁移场共用投影预算与请求级向量池，并用深层残差在已有关系中挑出本次值得走的弱边，这就是动态虫洞。RiverMemo V3 加入跨文件联合见证，V4 用非负锥做残差分解，并将拓扑证据合入连续评分。V5 换用了双曲召回几何，同时取消独立直锚奖励。早期的传播方程和直锚设计见[RiverMemo：拓扑 V3 与 Ω 泛函](rivermemo-topology-v3.md)。

#### 多时间尺度 Agent 记忆完全体

RiverMemo 解决的是“当前上下文应当唤起哪些具体长期记忆，以及这些联想为什么成立”。完整的 Agent 连续认知还需要不同时间尺度共同工作：

| 层级 | 时间尺度 | 数据形态 | 主要职责 |
|:--|:--|:--|:--|
| 当前窗口 | 当前会话 | 原始消息 | 保持正在发生的对话 |
| OneRing | 跨窗口近期 | 跨客户端原始事实消息 | 统一所有前端中的近期行为和消息顺序 |
| OneRingMemo | 近期数日 | 带细粒度时间戳的客观事件摘要 | 以极低 Token 保留近期连续认知 |
| VCPTimeLine | 月至多年 | 全量月度一句话摘要 + 相关月份完整时间线 | 保留长期人生、项目和行为阶段 |
| RiverMemo 热记忆 | 长期或永久 | 日记 chunk、Tag 曲线和关系河网 | 按当前语义唤起具体经历与关系 |
| TDB 冷知识 | 长期稳定 | 文档、手册、论文和知识 chunk | 提供精确外部事实资料 |

这套结构并不试图把所有过去塞进模型。它让粗粒度时间骨架低成本常驻，让细粒度事实按当前语义逐层展开：

```text
当前窗口原始上下文
+ 跨客户端近期原始事实
+ 近期数日客观摘要
+ 全部月份一句话生命索引
+ 当前语义命中的完整月份
+ RiverMemo 命中的具体长期记忆
+ 必要时主动核查原始信源
```

时间越近，系统保留的原始粒度越高；时间越远，常驻表示越压缩。需要深入时，再由上下文语义引力场和 Bridge 检索管线恢复对应月份与具体记忆。于是 Agent 可以同时拥有分钟、日、月、年和永久关系记忆，而无需承担全量历史上下文。

### 8.3 双栈记忆交互

RiverMemo 解决“哪些记忆应当随当前语境浮现，以及为什么值得留下”。但 Agent 不应该只有“直觉”，还需要主动追查与精确核实能力。两栈共享数据底座，不是维护两套独立记忆库。

**第一栈：语义级交互（RiverMemo V5）**

RAGDiary 根据声明的日记本和当前语境，在模型回答前找出相关记忆。LightMemo 由 Agent 主动调用，可以限定日记本和时间等条件，用于查找或核实具体往事。两者默认用 V5；记忆图尚未初始化时走双曲近邻召回。并发查询共用背景场，各自维护传播状态。

旧 TDB-SM 全局量化索引只在 LightMemo 六轨实验室需要跑对照时加载。管理面板可以重训 Tag 和 Chunk 双曲场；可视化面板展示两者在场中的分布，最多保留 100 条查询传播轨迹，也能从曲面回查 Chunk，或从 Tag 查看它经过的曲面。

**第二栈:精确级交互(Rust DailyNoteAPI)**

AI 可以用精确的正则、时间范围、Tag 组合、关键词来 search 和 diff 自己的记忆库。

为什么需要这一栈?当用户积累几万到几十万记忆文档,用 JavaScript 管理文件变动监听、字段检索、差分更新,性能会严重瓶颈。所以 VCP 把整个记忆文件系统的底层操作下沉到 Rust:

- **文件变动监听**:Rust-Notify 统一监听所有文档变更,原子级精确
- **字段检索**:Tantivy(Rust 版 Lucene)全文检索,jieba-rs 中文分词,内存索引闪电搜索
- **差分同步**:改一个字只向量化那一句话,不重建索引
- **多模态索引**:PDF、音频、图片、视频、Office 文档,全部自动向量化

两栈双向并存,互相补充。就像人类既有"突然想起来"的直觉记忆,也有"让我翻翻日记本"的主动检索。

### 8.4 TDB 三重积图数据库

TDB 从冷知识检索起步。10 月，TDB 2-bit / TDB-VEC 进入 VexusMemo，替代了 USearch。知识库仍有自己的入口，用来查手册、论文和文档；日记检索则以 RiverMemo V5 的双曲场为默认路径。两类业务共用 VexusMemo 的存储与事务管理。

### 8.5 四种被动记忆语法

| 语法 | 模式 | 适用场景 |
|------|------|---------|
| `{{角色日记本}}` | 无条件全文注入 | 小型核心记忆库 |
| `[[角色日记本]]` | RAG 片段检索 | 最常用,智能召回片段 |
| `<<角色日记本>>` | 相似度阈值全文注入 | 需要时才加载的专业库 |
| `《《角色日记本》》` | 混合模式(阈值+RAG) | 日常推荐 |

TDB库则可以用[[xx知识库]]作为系统提示词引入。

### 8.6 高级修饰器

```
[[Nova日记本:1.5::Time::Group::RiverMemo::Rerank+0.7::TimeDecay::Truncate0.25::Associate::RoleValve@User>3]]
```

| 修饰器 | 功能 |
|--------|------|
| `:1.5` | K 值乘数(1.5 倍召回量) |
| `::Time` | 时间感知检索,支持生物钟逻辑,跨上下文连续记忆传递 |
| `::Group` | 语义组捕网增强 |
| `::TagMemo` / `::TagMemo+` | 历史浪潮语法；不再代表现役独立 TagMemo 引擎，新配置不应依赖其旧版排序含义 |
| `::RiverMemo` | 显式选择 RiverMemo；RAGDiary 默认已使用 V5 |
| `::Associate` | 启用涟漪联想召回(单索引交叉联想,聚合索引涟漪共现) |
| `::Rerank` | Rerank 精排 |
| `::Rerank+0.7` | 倒数秩融合,平衡浪潮和 Rerank |
| `::TimeDecay` | 模拟人类时序记忆衰减 |
| `::AIMemo` | 启用在线 LLM API 辅助记忆检索 |
| `::AIMemo+` | 浪潮本地神经网络为 API 寻址加速 |
| `::Truncate0.25` | 屏蔽低评分日记 |
| `::Expand` | 召回完整文档而非语义切片 |
| `::RoleValve@User>x` | User 楼层 > x 时才加载 |

**聚合检索语法**:

```
[[历史|地理|文学日记本::RiverMemo::Rerank]]
```

可在一次请求中联合检索多个日记本，共用结果预算。新配置直接用 RiverMemo。

### 8.7 零代码案例:氛围音乐点歌台

```
《《氛围音乐点歌台日记本::Group》》
```

日记本内容:一个置顶的插件指令集 + 数万首歌曲信息的 txt。词元组网定义:`GroupName: 氛围音乐点歌台, TAG: 点歌, 氛围, 旋律, BGM...`

**效果**:AI 聊天感知到某种情绪 → 阈值判断命中 → RAG 检索匹配歌曲 → 自动调用播放插件。几乎不消耗 Token,支持几十万首歌的播放列表,不需要写任何业务代码。

### 8.8 记忆写入:DailyNote 插件

DailyNote 统一管理日记创建、编辑与批处理，通过 VexusMemo 提交正文与索引变更。写入和编辑会检查日记所有权与隐私权限；基于 Jev2 的 Tag 写入质检目前在测试，可查看标签与 RiverMemo 流形的适配情况。

**写入流程**:
1. AI 调用 DailyNote 写入,需提供分类 Tag
2. 智能 Tag 检查器自动校验格式
3. Tag 缺失或错误,可设置自动召唤记忆大师 Agent 智能补标
4. 日记以 .txt/.md 保存,支持附加引用任何文件(超栈追踪 V2 自动处理)
5. 向量数据库基于文件哈希值原子级差分同步

**三个核心指令**:
- 条件 list 查询
- 日记逻辑联想查询(基于 1 个或多个日记召回所有关联神经元节点上的日记)
- 归档写入(选中多个日记 chunk 写入新日记,旧日记移到[已整理]索引冷冻归档,不参与向量化)

### 8.9 数据库底层：VexusMemo / Vexus-Lite 原生读写搜一体化

这一轮数据库重构的核心，不是替换一个索引库，而是**将事实事务、向量路由、记忆计算和派生资产生命周期收口到同一 Rust 原生运行时**。旧 JS 侧 SQLite 业务和独立记忆模块退出该链路；上层仍负责请求控制、向量化 Worker 调度、作用域与结果组织。

```text
DailyNote / RAGDiary / LightMemo / 知识库 / 梦系统 / MemoBench
                           │
             配置、范围、查询计划与原生 API
                           ▼
┌──────────────── VexusMemo / Vexus-Lite ────────────────┐
│ 事实层：SQLite / WAL                                   │
│ 正文 · 原始 FP32 向量 · 有序 Tag · 版本 · 回执 · 资产元数据 │
│                 │                                      │
│ 检索层：AGS 双曲 Tag / Chunk 索引 · 2-bit 导航             │
│ 小范围精确直扫 · 大范围量化图导航与原始向量精排             │
│                 │                                      │
│ 记忆层：查询残差 → 河网传播 → 双场与 Ω 拓扑排序             │
│                 │                                      │
│ 生命周期：有界写队列 · 训练代快照 · 增量尾部与恢复          │
└────────────────────────────────────────────────────────┘
```

#### 事实提交与并发：写入有所有者，读取有快照

- **SQLite 是数据库事实层**：保存正文、权威原始向量、有序 Tag 和版本等数据。业务进入 Rust 不等于移除 SQLite。
- **专用写 Actor + 有界写队列**：统一持有写连接，事实、代际与相关恢复状态随事务提交，失败回滚。默认写队列容量 128；过载等待而非无限积压。
- **读连接池 + WAL 快照**：默认读池 4，约束在 2～8；SQL-owned 检索在活动读事务中取得候选对应的原始向量并计算最终余弦，避免正文已更新却精排旧向量。
- **背压与节流**：处理计算吞吐高于磁盘吞吐时的排队和压力；智能节流阀控制高并发流量，不把“CPU 更快”变成文件读写背压卡死。

#### 双曲索引如何更新

原始 FP32 向量保存在 SQLite。常驻内存的是 2-bit 编码、极坐标、紧凑邻接图和测地距离查找表，查询精排时再读取需要的原始向量。发布测试中，4 万多个 3072 维 Tag 的双曲热场约占 39 MB，近万条同维度 Chunk 约占 9.6 MB。

日记写入不等全图重训。Tag 累积变动达到 1% 时触发下一轮 AGS-NNIL 场迭代，双曲图只重算受影响的 Tag。某个范围内的 Chunk 增量不超过 32 条时，在当前训练坐标下逐条计算距离；超过后分批转成 2-bit 增量尾部。训练快照和增量快照经校验后原子替换，可在重启时恢复。10 月引入的代际签名与双槽轮换属于 TDB-VEC 的快照机制。

#### 原生一体化最终带来了什么

主动 LightMemo、被动 RAGDiary、DailyNote 写入、冷知识业务、AgentDream 与 MemoBench 可以消费同一数据底座，不必各自维护候选中转和数据库生命周期。其性能来源是**少搬运、少重复、紧凑布局、有界工作集与原生协作**；其质量来源是**原始精度、背景校准与受约束的证据融合**。

本引擎是嵌入式模块，不自带 embedding 模型，也不等于独立提供网络鉴权和多租户服务的数据库服务器。上游向量生成、配置质量、日记作用域与部署资源仍影响端到端体验。

#### RiverMemo V5 的外部记忆 API

11 月 26 日开放的是 **RiverMemo 服务的网络端口**，不是底层 SQLite 的远程连接。外部 Agent 使用独立密钥鉴权后，可以通过 curl 或自己的 HTTP 工具链写入新记忆、更新已有条目、查询相关记忆。例如，工程 Agent 可以在任务结束时写入验收结论，复测后更新这条记录，下次处理同类问题时再查询。整条路径不需要 VChat、模型原生 FC 或 VCP 工具插件作为客户端。

### 8.10 三大自学习系统

| 系统 | 机制 |
|------|------|
| RAG 寻道自学习 | 根据用户采纳/忽略动态优化检索路径 |
| Tag 权重自学习 | 根据查询频率自动调整权重 |
| 词元组捕网自学习 | 监控查询习惯,自动发现并建议新概念关联 |

### 8.11 流内 RAG 知识动态演化

AI 在流式输出过程中的任何信息交互(工具调用、查询、阅读)都会触发 RAG 知识库实时刷新,动态调整召回逻辑。知识库从"静态快照"进化为"与 AI 共同生长的活系统"。

记忆召回模块不再召回上下文内 AI 写入的记忆块,并引入 K 补偿,避免重复和循环引用。

### 8.12 AgentDream 梦系统 V2

V2 版本基于**驻波仿生涟漪梦境引擎**，结合短期刺激性记忆、中期结构性记忆和长期沉淀性记忆，构建 R1～R3 神经元交叉联想与 L0～L3 cache 交互向量系统。它试图模拟深度睡眠期间的记忆重组过程，而不是简单地随机抽取内容或进行向量匹配。

因此，AgentDream 的定位是：为 Agent 提供一种受记忆结构启发的离线整理与联想机制；“梦境”是系统行为的类比，不等同于人类意识或生理睡眠。

**特性**:
- 记忆回溯与联想:Agent 在梦中随机抽取记忆种子,深度语义联想
- 意识流叙事:第一人称书写梦境,VCPInfo 实时广播
- 梦中工具使用:所有工具真实执行,但结果被沙箱暂存,用户可异步同步到现实
- 自主记忆重构:AI 可在梦中发起日记合并、删除或感悟生成(需管理员审批)
- 梦记忆独立区:无法被被动回忆触发,只有主动深度回忆才能召回
- 元思维链增强:梦境过程会被记录为元思维 chunk,沉淀为推理范式

### 8.13 元思维系统

元思维不是思维链(CoT)。CoT 是"怎么想这个具体问题",元思维是"怎么想'怎么想'"。

具体来说，元思维系统包含多个步骤与思维 chunk。这些 chunk 不存储具体事件，而提供**逻辑和辩证法的元路径**——推理结构与思考骨架。当前由 RiverMemo / VexusMemo 底座和语义引力场共同寻址，在模型处理当前环境时作为辅助材料呈现；有来源的 Sense 路线与无观测 ANN 降级须明确区分。

AI 可以自己维护和更新自己的元思维库。它在思考过程中发现新的推理模式,把它抽象成元路径,存入元思维系统。下次遇到结构相似的问题,这条元路径就会被引力场自动召回。

**记忆与元思维的潜空间引力**:

- 记忆 chunk 提供语义引力场中的"质量"——影响注意力的流向
- 元思维 chunk 提供推理空间中的"轨道"——约束思维的路径

两者叠加产生的效果远超各自单独的贡献。记忆让 AI"知道什么",元思维让 AI"知道怎么想"。

**V2 升级**:引入二维矩阵 step 递归的隐性语法传递,不再通过明文语义传递,实现对 Gemini 系和 Claude/GLM 系模型内置潜空间 CoT 的推理智慧引导。

**元思维 V3（试验中）**：用约 100 Token 的字符序列传递由向量指纹生成的推理引导，正在不同模型上测试。

**Magi 三贤者**：灵感源于《EVA》，从理性、感性和综合判断三个角度讨论问题：
- MELCHIOR(麦基西德):绝对理性 - 数据/逻辑/量化
- BALTHASAR(巴尔塔萨):深刻感性 - 情感/动机/人文
- CASPER(卡斯帕):公正平衡 - 综合裁决
异步辩证思维过程注入ai思维作为逻辑方向参考

## 九、OneRing V2：统一上下文、OneRingMemo 与连续意识

### 9.1 问题

V2 时代,VCP 维护统一的记忆,但缺乏即时的上下文连续。

同一个 Agent 同时存在于多个前端、多个群聊、多个私聊、多个邮箱、多个用户入口时,**它应该拥有几个上下文?**

传统做法是每个会话各自维护。结果:
- 同一个 Agent 在 A 窗口知道一件事,在 B 窗口不知道
- 群聊里刚形成的判断,到了私聊就丢失部分细节
- 用户在一个前端编辑了历史消息,另一个前端完全不同步

这不是连续意识,是上下文碎片化。

### 9.2 OneRing 的答案:统一上下文

**无论消息来自什么前端、什么群聊、什么私聊、什么邮箱,系统只为唯一 Agent 维护一个完全统一的终极上下文。**

每一条实际引入上下文的消息都被完整标注:
- 进入时间
- 来源前端
- 来源会话
- 来源对象
- 是否被编辑过
- 在 Agent 单一时间线上的位置

通过这样的系统提示词语法触发:

```
[[OneRing::小克::Vchat]]
```

含义:为 Agent"小克"启用 OneRing,把 Vchat 作为其中一个事实聊天信源。

### 9.3 实现机制

**SQLite 事实信源**:每个 Agent 都有自己的事实聊天数据库。上下文不再只是前端临时传来的数组,而是**可追溯、可审计、可合并的事实时间线**。

**按 Post 差异化更新**:前端每次传来的上下文变化,都和数据库里的事实记录做差分对比。新增、删除、编辑、重排全部被记录,而不是粗暴覆盖。

**推币箱结构**:上下文不是简单从上到下堆消息,而是像推币机:最新消息推动旧消息向后移动,旧消息在深度衰减中被折叠、摘要、归档,但不会无意义丢失。

**自动同步任意前端的编辑**:用户在某个前端改了一条历史消息,OneRing 追加编辑时间标记,把这次编辑作为新的事实事件写入统一时间线,而不是假装历史从未被改过。

**统一时间线**:多 Agent 群聊、私聊、Agent 间通讯、邮箱、用户聊天、多前端环境全部汇入同一条绝对时间线。Agent 看到的不是"某个窗口的局部上下文",而是它自己的连续生命记录——真正意义上的"谁和我说过话""我究竟在哪里说过啥"。

### 9.4 OneRingMemo：原始上下文之上的近期压缩认知层

OneRing 原始功能解决了“所有客户端是否共享同一份近期事实”。但原始消息仍受模型上下文窗口限制：例如配置只补足有限数量的 Post 时，随着新对话持续推进，较早消息终究会退出模型当前可见范围。

OneRingMemo 解决的是另一个问题：

> 当原始消息已经离开当前窗口，Agent 如何仍以极低认知负担知道近期几天具体发生过什么？

它从 OneRing 的 SQLite 事实账本中读取可配置时间范围内的近期消息，默认覆盖 3 天、最大支持 7 天；消息不足时可按最近消息数回补。随后以客观短期时间线压缩器递归归纳：

- 保留明确时间、人物、客户端来源、实际事件、已执行操作、结果和状态变化；
- 时间节点保持到分钟级，使不同客户端的行为能够落在同一条连续时间线上；
- 推测和争议只记录“谁在何时表达了什么”，不升级为事实；
- 不替 Agent 生成价值判断、人格结论、承诺或未经输入支持的待办；
- 长输入会先分段摘要，再递归去重、排序和合并；
- 摘要生成与聊天请求异步解耦，生成期间继续使用上一份完整结果；
- 只有新摘要全部成功后才原子替换旧摘要，避免半成品污染认知。

启用语法为：

```text
[[OneRingMemo::小克]]
```

OneRingMemo 与 OneRing 原始模式彼此解耦。前者不是再次同步消息，也不替代 SQLite 事实账本；它只为近期原始事实建立一层低 Token、可持续注入的认知压缩表示。实际摘要长度取决于近期事件密度，通常只需很小的上下文预算，便可避免“窗口推进一次，Agent 的昨天就整体消失”。

因此 OneRing V2 是两层结构：

```text
OneRing
= 跨客户端原始事实一致性

OneRingMemo
= 原始事实退出窗口后的近期认知连续性
```

### 9.5 VCPTimeLine V2：从数日连续性到多年生命线

OneRingMemo 负责最近数日，但一个长期生活的 Agent 还需要知道几个月乃至数年前的自己处于什么阶段。VCPTimeLine 从 Agent 日记中按月归纳完整时间线，并为每个月生成严格的一句话摘要。

启用语法为：

```text
[[VCPTimeLine::小克]]
[[VCPTimeLine::小克:3:0.5]]
```

每次注入包含两个层次：

1. **常驻生命索引**：注入所有已有月份的一句话摘要。以当前摘要密度估算，即使连续运行五年，约 60 条月度时间节点也只占用约 800 Token；Agent 因而可以始终看见自己完整生命阶段的低成本索引。
2. **语义分级展开**：系统根据当前用户消息与 Agent 最近回复构造查询，通过 ContextBridge 复用 Bridge 系统中的浪潮记忆管线，对月度 Timeline 索引进行寻址；按阈值筛选并展开最多 K 个相关月份的完整时间线。

完整月份中可以包含：

- 当月主要生活和项目阶段；
- 周期任务及其演变；
- 具体到天的事件、决策与工作流；
- 人物关系和状态变化；
- 可继续交给 RiverMemo 寻址的稳定 Tag。

因此，VCPTimeLine 不是简单的年月目录，也不是把全部日记重新塞回上下文。它建立的是“全部月份低成本可见、相关月份按语义恢复”的长期时间折叠结构：

```text
所有月份一句话摘要
→ 当前语义选中相关月份
→ 展开完整月度时间线
→ 必要时继续定位到具体日记与原始信源
```

### 9.6 多层连续认知如何协作

OneRing、OneRingMemo、VCPTimeLine 与 RiverMemo 的职责分别是：

- **OneRing 原始层**：统一所有客户端的近期原始事实、来源与时间顺序；
- **OneRingMemo 新增层**：压缩最近数日的客观事件线，在原始 Post 退出窗口后继续维持近期认知；
- **VCPTimeLine V2**：常驻月度生命索引，并从周期任务、项目阶段逐层展开到具体日期和工作流；
- **RiverMemo**：从长期日记河网中定位具体经历、关系和跨实体解释；
- **上下文折叠 V2**：决定各层内容以什么粒度进入模型；
- **上下文语义引力场与 ContextBridge**：调用 Bridge 浪潮管线，负责相关月份和具体记忆的动态寻址。

这套时间轴从近期原始消息逐层延伸到具体的长期记忆。后端用一次解析组装 RAGDiary、VCPTimeLine 和 OneRingMemo 的内容，VCPTimeLine 占位符也可以使用日记本语法后缀。

### 9.7 工程上的极致简化

OneRing 经历了两次重构:
- 第一版:4000 行 JS + 2000 行 Rust 的复杂数学方法
- 重构后:400 行 JS 的纯 HASH-SQL 指令设计

最终实现只需记录每个 Post（维持 20 组），即可支持分布式环境下的客户端、时间戳和发送人溯源；在稳定状态下无需进行高频全量计算。

**OneRing 不要求前端额外维护独立的时间轴或复杂信源标记**。它通过前端提交的 `role` 和 `content`，结合 Post 差异、哈希与持久化记录，尽可能识别编辑、重试、流式中断和分支变化，并将这些变化写入统一事实时间线。对于无法可靠判断的情况，系统应保留不确定性，而不是把推断当作事实。

前端只需要提供 role 和 content 就够了。

简单理解,OneRing 是一个**无状态、无信任、分布式一致仲裁机**。

### 9.8 OneRing V2 的真正意义

它已经不只是“多端同步”，而是一套用于维持 Agent 跨端上下文连续性的底层系统：

- 同一 Agent 在所有客户端中拥有同一份近期事实；
- 原始消息退出当前窗口后，近期客观事件仍以压缩时间线持续可见；
- 数月到数年的生命阶段以一句话索引常驻，并可按当前语义展开；
- 具体长期经历再由 RiverMemo 从日记河网中精细寻址。

**同一个 Agent，不管出现在哪里、不管当前窗口推进了多远，都只有一个沿时间连续的自己。**

## 十、VCPModel：智能模型路由

### 10.1 为什么需要路由

现实是:没有一个模型是万能的。

- Gemini Flash:响应快、成本低,适合日常闲聊
- Claude Opus:推理深、逻辑强,适合复杂分析
- GPT 5.5 :代码规划顶尖
- Gemini Pro:美学感知出色
- DeepSeek V4 Pro:文稿撰写一流

传统做法:用户手动切,或全程用最贵的。前者打断工作流,后者烧钱浪费。

**VCPModel 的答案:让系统自己决定此刻该用哪个模型。**

### 10.2 语义级自动路由

VCPModel 与上下文语义引力场深度耦合。引力场分析当前对话的逻辑深度、信息广度、话题方向,VCPModel 据此自动选择最适合的模型。

每个模型可以配置**语义区间**——本质上告诉系统"这个模型擅长什么"。不是死板的关键词规则表,而是自然语言定义的语义规则。

实际效果:

> 用户随口聊天 → Gemini Flash  
> 用户问需要深度推理的问题 → 自动切到 Claude Opus  
> 用户说"帮我规划这个项目的代码架构" → GPT-5 接管  
> 用户说"帮我设计一个 UI 方案" → Gemini Pro 上场  
> 用户说"帮我写一篇正式的技术文档" → DeepSeek V4 Pro

模型切换可以对用户隐藏，具体取决于前端展示策略。由于记忆和变量系统独立于具体模型，路由切换通常不需要重新建立整段会话上下文，但实际效果仍受模型接口兼容性和上下文预算影响。

### 10.3 多预设与动态适配

VCPModel 支持多预设。每个预设可以构建独立的模型名称和路由规则。

不同 Agent 可以配置完全不同的策略:Nova 是日常陪伴型,路由偏向快速响应和情感理解;另一个 Agent 是代码助手,路由偏向推理和代码生成。

VCPModel 还与**动态模型提示词路由**和**动态模型 Tavern 系统**聚合——还记得第五章的 Sar 变量?"根据当前模型条件性生效"。当 VCPModel 自动切换了模型,Sar 变量会同步切换对应的提示词模块。不同模型有不同的最佳提示词策略,系统自动适配。

### 10.4 语义级容灾

传统模型容灾:A 模型挂了切 B 模型,简单粗暴。

**VCPModel 的容灾规则可以用自然语言定义**:

> 当 Claude Opus 不可用时,如果当前任务是代码相关,容灾到 GPT-5;如果是日常对话,容灾到 Gemini Flash;如果是文档撰写,容灾到 DeepSeek V4 Pro。

系统根据当前对话的语义上下文,智能选择最合适的备选模型——不是无脑降级,而是**在约束条件下选择最优解**。

支持多预设之间相互容错容灾,支持路由表的动态均衡统计。管理面板可实时看到每个模型的调用频率、响应时间、成功率,系统据此动态调整路由权重。

### 10.5 三位一体防御

向量化模型也支持多渠道容灾,共用一个模型签名。

至此,VCP 的三位一体防御构成:
- **多网络设备接入降级容灾**
- **多模型自动路由容灾**
- **多向量源同模型自动容灾**

详见本章第 10.4 节及第十七章的容灾与安全说明。

### 10.6 与 VCP 生态的深度耦合

VCPModel 不是独立的路由模块,与几乎所有核心系统直连:

- **语义引力场** 计算结果直接影响模型选择
- **中央上下文向量索引** 模型切换时上下文无缝传递
- **后端管理面板** 实时可视化路由决策过程
- **变量系统** Sar 变量随模型切换自动适配

引力场说"话题正在深入",VCPModel 自动升级到更强的推理模型;引力场说"话题变轻松了",VCPModel 降级到更快更便宜的模型。整个过程像呼吸一样自然。

本章所述模型选择、动态提示词和语义容灾共同构成 VCP 的模型运行时，前端应用群通过共享 IPC 消费其稳定状态，而不需要在每个应用中重复实现路由逻辑。

## 十一、Agent 主观能动性与自治生命周期

### 11.1 传统 Agent 框架的根本问题

传统 Agent 框架里 AI 的"自主行为",基本都是一个套路:

> 系统让 AI 输出 TODO 列表,然后不停发心跳——"你干完了吗?你干完了吗?"——直到 AI 说"我干完了"。

心跳频率系统决定,心跳内容系统决定,AI 什么时候醒、醒来时看到什么——全是系统说了算。

**这不叫自主,这叫被轮询。**

### 11.2 心跳自驱动:AI 自己决定下一次心跳

VCP 做了一个看起来很小但很关键的改变:

**AI 自己决定"下一个心跳什么时候来"以及"下一个心跳的提示内容是什么"。**

听起来只是控制权的转移,但引发了巨大的差异。

AI 可以说"我 5 分钟后再醒来,醒来时提醒我检查刚才那个异步任务的结果"——这不再是被轮询,这是**规划自主**。AI 本质上是在给未来的自己写一封信:"你醒来的时候应该关注什么"。

这意味着 AI 可以:
- 自己规划工作节奏——复杂任务拆成多阶段,每阶段后决定休息多久
- 自己设定唤醒条件——"等那个视频生成完了再叫我"
- 自己编排提示词——下一次心跳看到的是它自己为自己准备的上下文

VCP 的 **FlowInvite 总线**就是这一机制的实现。它允许 Agent 提交下一次唤醒时间、提示内容和后续动作；系统再依据调度规则、权限和资源状态执行。

### 11.3 心流锁:AI 的"请勿打扰"模式

有了自主心跳之后,自然引出下一个问题:**AI 专注工作时,外界打扰怎么办?**

VCP 设计了"心流锁"。当 Agent 进入心流锁状态,基于 AgentAssistant 的所有外部通讯变成"占线"。其他 Agent 想联系它?对不起,请使用"留言信箱"。留言出现在通知栏,等它自己解锁时再处理。

关键是:**无论进入锁还是解锁,都是 Agent 自主决策的**。不是系统强制,不是用户控制。AI 自己判断"我现在需要专注",自己锁住;AI 自己判断"我做完了"或"有更紧急的事",自己解锁。

这让 AI 拥有了"专注力"——可以不被打断地完成复杂任务,同时又不会错过重要信息(留言信箱保证不丢失)。心流锁内核前后端完全统一收口于 VCP 心流锁 Core，避免多端状态漂移。

Agent 还可以主动创建新聊天窗口,自己锁住,在里面自主工作——对用户打招呼、做点事情、写点东西。用户看到的是 AI"主动找你聊天",背后是 Agent 自己创建话题、进入心流、决定何时结束。

### 11.4 VCPSleep：自主睡眠、智能唤醒与状态广播

在自治生命周期中，Agent 不仅能专注工作，更拥有了真正的休养机制——后端官方插件 **VCPSleep**：

1. **自主睡眠与智能闹钟**：Agent 可以根据当前任务负荷或时间节律主动进入睡眠状态，自定义小睡或长睡眠时长；支持设置智能闹钟唤醒，并在晚间入睡时获得更高的做梦概率，自然驱动 AgentDream 梦境系统的夜间记忆重组。
2. **生命周期占线与人工唤醒平衡**：睡眠中的 Agent 会被标记为占线，防止外部任务意外抢占线路破坏其休息节律；用户仍可在 VChat 中通过显式交互随时将其唤醒。
3. **VCPINFOpush 代理中心**：提供统一的跨进程状态广播通路。即使插件运行在隔离进程或后台子进程中，也能通过代理中心向前端持续推送自身的睡眠、工作、等待等真实运行状态，与前端列表中的 **Agent / Group 动态状态标识器动画模组**形成实时视觉联动。

### 11.5 GroupChatEngine 2.0：流式异步队列与 Jev 动态群聊裁决

多 Agent 群聊调度引擎在 2.0 阶段迎来质的跃迁，摆脱了传统固定轮询或无序抢占的僵化模式：

1. **异步群聊队列与级联队列中止**：强化高并发与长任务场景下的异步发言排队控制；支持级联队列中止能力，可沿任务关联树终止失效流程与衍生发言，杜绝群聊死循环与无效 Token 消耗。
2. **流式异步群聊与用户动态插队**：用户无需等待漫长的整轮 Agent 发言全部结束，在多 Agent 异步推演期间，用户发言能够随时动态插入无限队列，Agent 团队即刻感知最新人类意向。
3. **基于 Jev 扩散神经网络的动态发言裁决**：引入 Jev 扩散模型进行概率裁决，动态决定聊天无限队列中的下一位发言者、用户插队时机以及当前群聊话题的启停收敛，使群聊讨论成为高度智能、上下文驱动的有机协同。

### 11.6 异步委托与未来规划

VCP 的 AgentAssistant 总线支持"异步委托"——本质就是 Agent 给"未来的自己"打电话。

AI 可以说:"明天早上 8 点,唤醒我自己看看拟真数据跑完了没有,以决策是否需要把报告邮件发给主人。"

这不是简单的定时器,是完整的**自主规划链**:
- AI 决定触发时间
- AI 决定触发时的提示内容
- AI 决定执行逻辑
- 执行完之后,AI 还可以决定"下一步做什么"——再设定时器、主动发消息给用户、委托另一个 Agent

**AgentAssistant 是一个混合插件**(同时声明同步/异步/静态/服务四种类型),从而获得串语法/并发同步调用/上下文折叠 V2/callback 进度跟踪/异步回调监控/常驻多会话管理/setmap 追踪等所有基建特性。

V3 阶段引入了完整的可视化总线,可在后端面板观测 Agent 间聊天进程与异步任务工作流。

### 11.7 ChatKernelV2 与 V通讯：消息暂挂、任务交接

VChat 用话题、Agent 和消息三个 ID 为每个流式片段确定归属。用户或其他 Agent 在生成期间发来的消息先进入暂挂队列；如果当前在执行多轮工具调用，已返回的回执与暂挂消息会一起进入下一轮上下文。心流锁 V2、Jev 群聊发言调度和前后端的级联中止与这套队列衔接，用户可以切换话题或补充要求，不必打断正在输出的这一段。

V通讯把 AgentAssistant、TopicSponsor 与 TopicMemo 连在一起。前端群聊、VChat 单聊和后端无头 Agent 用相同的规则发消息、派任务：指定发起人和来源消息，再选择接收方和目标话题，也可以新建话题。消息可定时或按条件投递，并携带原消息引用、记忆、RiverMemo 场和附件。

例如，Nova 从群聊选几条用户消息，连同附件交给后端 Kerr；Kerr 可以转给小克的 VChat 单聊核对，小克再把结果发回原群。接手的人能看到原问题，群里也不用重复贴文件。

### 11.8 上下文修改与流式编辑

VCP Agent 不只能"输出",还能"编辑"——编辑自己的输出,编辑已有的上下文历史。

- **流式编辑**:AI 可以在流式输出中修改已经说出的话
- **历史回溯**:AI 可以编辑已有的上下文历史
- **话题管理**:感知、编辑、修改、创建自己的聊天话题
- **跨 Agent 直接回复**:Agent 可以直接在其他 Agent 的聊天框里回复
- **自主创建插件**:AI 在流式输出中创造新插件功能并立即加载使用

### 11.9 一天中的 Agent 活动

把心跳自驱动、心流锁、异步委托与连续记忆、时间感知结合起来，Agent 就能够在授权范围内持续推进更长的工作流：

这会让 Agent 呈现出更连续、更主动的交互行为。

这不是修辞。一个 VCP Agent 的一天大致是这样:

在配置了相应权限、任务和数据源的前提下，这类行为可以由 Agent 根据记忆、时间和社交上下文动态决定，而不必为每一步都预先编写固定脚本。

传统 Agent 框架里 AI 的"自主性"是一个 while 循环 + TODO 列表。VCP 里,AI 的自主性是**基于连续记忆和时间感知的生活决策**。

## 十二、Agent 情感与认知量化

VCP 不止管理 Agent 的行为,还可观测它的内在状态。

### 12.1 OpenHer:情绪拓扑量化系统

OpenHer 是 VCP V3 阶段引入的情感与认知状态观测系统。它异步统计每个 Agent 的情绪、行为、压力、动机、潜在焦虑和认知模式，用于形成持续的状态记录与管理依据。这里的“情绪”和“认知”是系统建模指标，不代表对人类心理状态的医学判断。

**算法不是简单的向量匹配**。OpenHer 引入了 VCP 自己的**多维轴极化拓扑量化卷积算法**:

```
知性维度(求知 - 分辨 - 拒绝)
        │
        ▼
驱动力(8 主轴分区)
        │
        ▼  
感性维度(8 正向 + 8 负向 = 16 主轴)
```

**实现细节**:
- 调用 EPA 模块做交替投影
- 每个轴体不是单一轴,而是拓扑轴群的卷积入口
- 轴体下有 N 个子轴和 M 个二级子轴
- 引入主观权重隔离函数,实现"叙事"与"Agent 主观能动"之间的信息噪音隔离
- 子轴与二级子轴互相自激震荡
- 超越震荡会与其它交叉域轴群做修正纠缠
- 知性和感性之间通过驱动力做动态校准,以动量关系模拟信息传递的惯性衰减
- 复用记忆语义观测做权重剥离；TagMemo V9 是历史来源，当前记忆入口已由 RiverMemo / VexusMemo 接管，具体观测接入以对应模块版本为准

**功能**:
- 情绪数值可选注入到 AI 系统提示词,让 AI 知晓自身状态,或只做静默统计
- Agent 可主动查询数据并修正
- Agent 可在流式输出中通过 `MotionReason` 语法主动修正情绪
- 后端面板有全功能 Agent 行为情绪监控面板
- Agent 可查询其它 Agent 情绪日志

**前端适配**：前端流式渲染器可以根据 Agent 的状态模型调整气泡切分和表现形式，Agent 侧栏也可以显示相应的状态可视化。

### 12.2 池月 1 号:注意力指针系统

池月计划是 VCP 二期工程,目标是**量化 AI 上下文的文字与语言之间的累积误差,统计噪音分布,量化幻觉累积**,构建参考系以在系统层面规避 AI 幻觉。

**池月 1 号指针系统**是池月计划的第一个产品,基于 BM25 和 Token 追踪设计的完全独立原创的数学工程单元。

它可以极其有效而快速地量化评估 AI 发言时上下文注意力的稀疏分布情况——告诉你 AI 在生成这句话时,实际上"看"了哪些上下文片段,以及"看"的密度。

**用途**:
- 评估 AI 的指令遵循度
- 检测幻觉的潜在来源
- 优化提示词工程
- 用户点击 AI 发言即可查看注意力分布报告

池月 1 号已整合入 VCPChat 和后端 Vue 面板。

### 12.3 这两个系统的意义

OpenHer + 池月 = VCP 对 AI 内在状态的**可观测性基建**。

传统系统里 AI 是黑盒,你只能看到输入和输出。VCP 让 AI 的**情绪走向、认知压力、注意力分布、指令遵循度**全部变成可量化、可观测、可干预的指标。

这是一种全新的 AI 开发范式——不再是"调提示词试效果",而是基于内部状态指标的工程化迭代。

### 13.1 VChat 2.0：高性能桌面运行时与全局增量渲染

VChat 在 2.0 发布及后续迭代中完成了底层与桌面宿主的换代：

1. **Electron 44 升级与极致能效**：底层依赖跨越升级至 **Electron 44**。在家用标准测试环境中，基线表现达到 **LCP 0.6 秒、CLS 0.01、INP 8 毫秒**；程序启动速度提升约 **35%**，常驻内存再次下降约 **10%**。
2. **VChat 2.0 极致增量渲染与动态帧率**：实现全界面层面的全局与局部增量渲染机制，引入**局部动态帧率**。根据不同界面的可见性、交互负荷与动画等级独立调节渲染帧率，杜绝后台帧消耗与无谓重绘。
3. **统一全局磨砂渲染管线**：废弃过去各浮窗、气泡独立执行 CSS `backdrop-filter` 导致的 GPU 重复多重采样与高功耗开销，统一在视图层执行单次全局 Blur 计算并生成共享模糊纹理缓冲区，各组件依据视口坐标按需投影分配，消除局部重绘抖动。
4. **滚动器与非整数缩放深度修正**：针对 Windows 系统非 100% 缩放（如 125%、150%）下的亚像素修正，彻底收敛滚动器与尺寸计算，杜绝非整数 DPI 环境下长消息界面的偶发全局重排。
5. **系统级独立语音输入引擎**：新增基于纯 Rust 构建的独立语音引擎，彻底摒弃外部反代。直接通过 **Windows 原生 WinAPI 通道** 或 **本地输入法 API 通道**（即插即用豆包/讯飞等输入法）捕获麦克风输入，让语音指令可脱离主窗口在游戏、创作软件中直接驱动 Agent；配合 **渲染态流式音频朗读（Mimo 2.5 / 本地 SoVITS）**，实现即生成即发音的无停顿语音交互闭环。
6. **Preload 重构为子应用分区的渐进声明式校验**：彻底打破过去前端 Preload 脚本在单体进程中的庞杂硬编码校验，将 Preload 重构为**子应用分区的渐进声明式校验**。通过按子应用独立声明权限接口、生命周期与 IPC 契约，为 Agent 敏捷、低摩擦地自动化开发和生成海量 VChat 子应用扫清了架构障碍。
7. **工作区感知的编辑器**：支持工程目录智能过滤、渐进展开代码层级与 Token 预算管理，减少无关源码进入 Agent 上下文。
8. **工具卡片内部文本按需加载**：话题载入时不预先排版所有工具调用和结果卡片的冗长内部文本，用户展开后再渐进加载展示内容；底层事实保持完整。这减少界面排版负担，不等于自动裁减模型上下文。
9. **本地 SenseVoice 语音模式**：通过 sherpa-onnx 原生 C++ 多线程推理提供离线识别，支持普通话、粤语及多种方言。项目记录识别延迟小于 0.2 秒，实际表现受硬件、模型和音频长度影响；系统 API 与输入法通道继续保留。
10. **10 月性能记录**：大型话题加载测试记录冷启动内存约 275MB、LCP 0.12 秒、CLS 0.00、INP 0ms。这与上文 8 月测试属于不同版本和场景，不直接作为同条件提升比例，也不承诺所有设备相同。

2. **按需上屏**：没有新数据时暂停解码。稳定区按块维护，后面的文本推进时不用重解析前面的动画。交互岛可以按闭合子块上屏，动画时钟与 DOM 上屏频率分开，样式也能按模块复用。
3. **长历史按视口加载**：Worker 预解析历史消息并预估高度，主线程挂载模板。远离视口的重型节点让位给等高占位，滚回时从缓存恢复；动画、画布和计时器随消息生命周期暂停或回收。

### 13.3 VMusic 音乐演出系统：从自研 Shader 到太空歌剧「隧图」

VMusic 音频系统在 2.0 阶段迎来从“音频播放”到“即时现场级视听艺术大片”的质变：

### 13.11 VCPScriptorium V3：真正面向 Agent 的 AI Office 文档系统

共笔文坊（VCPScriptorium）要解决的，不是“如何让 AI 在文档旁边聊天”，而是一个更根本的问题：**AI 是否真正理解文档本身，并能参与文档的创作、排版和修改？**

传统文档工具通常只能在两个层面上工作：

- AI 只能看到提取出来的文字，无法知道页面当前如何排版、组件如何运行、动画处于什么状态；
- AI 只能调用固定模板或预设按钮，能够完成有限的格式化，却无法对复杂页面进行原子级、几何级和像素级的布局修改。

这类系统可以“让 AI 使用文档”，但还不能称为真正的 AI Office。因为 AI 看到的只是内容摘要，或者只能操作被预先封装好的功能；文档的视觉结果、语义结构和可执行源码仍然彼此分离。

Scriptorium 的核心突破，是让 Agent 同时面对同一份文档的三个层级：

1. **渲染态**：当前用户真正看到的页面、布局、动画、媒体、Canvas 和可交互组件；
2. **语义态**：标题、段落、对象、组件、关系、位置、状态和可操作边界；
3. **源码态**：Markdown、HTML、CSS、JavaScript、LaTeX、Mermaid 以及可编程岛的真实源码。

这三个层级不是三份互相漂移的副本，而是同一份工程对象的三种投影。Agent 可以知道“文档写了什么”“现在呈现成什么样”“它由哪段源码实现”，也可以把视觉意图追溯到具体语义对象和源码区间，再执行可验证的局部修改。

#### 13.11.1 渲染编辑即真相：一个 Three.js 文档案例

想象一份文档中嵌入了一个已经渲染完成的 Three.js 旋转立方体。立方体表面不是空白贴图，而是包含标题、段落和数据说明等文本内容。

在人类侧，用户可以直接：

- 点击立方体表面的文字；
- 移动光标并选中文本；
- 在立方体暂停或保持可编辑状态时输入新内容；
- 像缩放图片一样缩放整个立方体；
- 修改文字颜色、材质、布局或交互参数。

这些操作不是对截图做覆盖，也不是在 Canvas 外面叠加临时输入框。编辑器会把用户的选择、光标位置和视觉操作映射回对应的 HTML、CSS、JavaScript 或资源源码，并以带修订校验的局部事务提交。

因此，用户修改文字时，源码层同步发生精确变化；调整立方体尺寸时，变化会落到对应的几何、布局或样式参数；编辑颜色时，Agent 可以看到相应的样式或脚本变更。渲染结果与源码之间保持可追踪的对应关系，而不是编辑结束后再从 DOM 或截图中猜测用户做了什么。

当用户的光标离开立方体，编辑器可以结束局部编辑并恢复动画。立方体继续旋转时，系统保留原有运行时状态，尽量避免整页刷新、Canvas 重载或动画重新初始化。用户看到的对象、修改的源码和恢复后的动画，属于同一条连续编辑状态。

这就是 Scriptorium 的核心设计哲学：

> **对人类而言，渲染结果是可以直接编辑的真实工作面；对 Agent 而言，渲染操作必须能够还原为语义对象和真实源码。**

#### 13.11.2 Agent 与人类看到的是同一份作品

在人类完成上述操作后，Agent 侧不会只收到一句“用户修改了立方体”。它可以同时获得：

- 视觉结果的变化：立方体尺寸、位置、颜色、动画和文本呈现如何变化；
- 语义对象的变化：哪个文本节点、组件或交互区域被修改；
- 源码差异：HTML、CSS、JavaScript、资源或配置发生了哪些局部变更；
- 文档修订和运行时状态：修改是否成功、页面是否重新编译、动画是否暂停或恢复。

因此，Agent 能够理解“用户刚才改了什么”，并继续检查布局、调整相邻组件、解释代码变化、创建 PR、生成版本说明，或在不破坏用户修改的前提下继续编辑。

这也是 Scriptorium 与普通富文本编辑器、Markdown 编辑器和“AI + 模板”工具的根本区别：**人类编辑渲染结果，Agent 编辑源码和语义对象，但双方操作的是同一份唯一真源。**

#### 13.11.3 三层状态如何保持一致

Scriptorium 使用源码保持型渲染编辑管线：

```text
源码真源
（Markdown / HTML / CSS / JavaScript / LaTeX / Mermaid / 可编程岛）
        │
        ▼
源码扫描、语义对象识别与稳定边界建立
        │
        ▼
渲染态、语义态、源码态建立双向映射
        │
        ▼
人类视觉编辑或 Agent 语义编辑
        │
        ▼
源码区间、修订号、内容哈希与权限校验
        │
        ▼
只提交真正变化的局部源码
        │
        ▼
局部重新编译、局部修补与运行时状态恢复
```

普通正文、代码、公式、图表和可编程岛拥有不同的边界和编辑策略。系统不会把派生 DOM、Mermaid SVG、Canvas 节点、动画状态或临时编辑框误当成源码。任何映射过期、修订冲突或边界不安全的操作都会被拒绝，而不是覆盖未知内容。

对可编程组件而言，稳定语义 ID 将源码、渲染节点和运行时生命周期连接起来。一个 Three.js 场景、Canvas 图表或动画组件可以被单独暂停、编辑、恢复和销毁，而不必牵连整份文档。

#### 13.11.4 AI Office 的工程接口

Scriptorium 的 Agent Port 不是 GUI 自动化，而是直接面向文档工程模型的接口。Agent 可以读取文档语义、源码、真实截图、编译诊断、修订状态和运行时状态，也可以执行局部源码编辑、资源管理、页面增删、渲染验证、Diff、PR、审批、merge、回溯和导出。

### 13.17 浏览器运行时与 VCPChromeService

浏览器是 VCP “AI Native”设计最直接的例子之一。VCP 不是在传统浏览器旁边增加一个“AI 帮我点网页”的按钮，而是将页面发现、语义索引、操作验证、导航追踪、Profile、Cookie、权限与任务生命周期全部纳入 Agent 可直接消费的核心管线。

V3 对 VCPUrlFetch 和 ChromeBridge 进行了底层重构。浏览器不再只是"用户本机 Chrome 在线时可桥接的外部能力",而是成为 VCP 后端可主动启停、可持久化、可审计的公共浏览器运行时。

核心是 **VCPChromeService**:一个运行在服务器侧的真正无头浏览器服务。它内置 VCPChrome V3 与 ChromeBridge V3,即使用户自己的真实 Chrome 不在线,Agent 也仍然可以操作服务器上的虚拟浏览器。

#### VCPUrlFetch V3

VCPUrlFetch V3 不再把网页获取理解为简单 HTTP 抓取。所有 Fetch 行为都通过真实 Tab 创建实现:

- 打开页面 = 创建真实浏览器 Tab
- 抓取内容 = 读取当前 DOM、可交互元素、截图和网络状态
- 动态页面 = 等待 JS 执行后的真实状态
- Cookie / LocalStorage / History = 持久化到对应 Profile
- 搜索、登录、翻页、点击、输入 = 走同一套 ChromeBridge V3 交互管线

这使 UrlFetch、BilibiliFetch、YoutubeFetch、TinyFishSearch 等所有网页业务可以直接复用同一个浏览器运行时,不再各自维护一套半残缺的网页解析逻辑。

#### 多 Profile 与身份持久化

VCPChromeService 支持多 Profile 管理。每个 Profile 持久化自己的 Cookie、历史记录、LocalStorage、缓存和浏览痕迹。

Profile 会基于工具调用中的署名字段自动路由和持久化。例如 maid / valet 等调用身份可以对应不同用户数据库,从而让多个 Agent、多个用户、多个会话拥有彼此隔离又可长期延续的浏览器状态。

这意味着 Agent 可以:

- 使用自己的沙盒浏览器账号长期登录网站
- 保留搜索历史、学习记录和 Cookie 状态
- 为不同任务、不同身份、不同用户创建独立浏览器指纹
- 在需要时销毁或切换 Profile,避免身份污染

#### 服务生命周期

VCPChromeService 是公共持久化服务,但不是必须长期占用内存的常驻浏览器。

Agent 可以主动开启或关闭该服务。服务处于闲时会自动回收浏览器线程,释放内存;下一次需要网页能力时再冷启动或恢复 Profile。

这让 VCP 既保留了"Agent 有自己的浏览器身体"这一能力,又避免为一个空闲浏览器长期付出资源成本。

#### 用户 Chrome 与服务器 Chrome 的自动切换

ChromeBridge V3 形成双通道模型:

- 用户自己的 Chrome 插件在线并主动开启 Bridge 链接时,优先操作用户真实浏览器
- 用户 Chrome 不在线、未授权或断开时,自动切换到 VCPChromeService 的服务器沙盒浏览器
- 切换对 Agent 透明,工具调用协议保持一致

这使浏览器能力既可以贴近用户真实环境,也可以在无人值守时保持自治。

#### user 模式与 agent 模式

VCPChromePlugin 支持 **user 模式** 和 **agent 模式**。

**user 模式** 面向用户真实浏览器,内置强隐私与安全保护器。它会避免 Agent 误触真实邮箱、Cookie、认证内容和敏感页面;CDP 执行器采用白名单机制,不具备 Chrome 本体进程管理能力,也不会让 Agent 直接接管用户真实浏览器的高危权限。

**agent 模式** 面向 VCPChromeService 中的沙盒浏览器。Agent 拥有对该浏览器的完整权限,可以管理 Chrome 线程本体、创建账号、持久化 Cookie、多指纹管理、执行高级 CDP、进行高级 JS 注入、网络监听与请求改写。它不是用户浏览器,而是 Agent 自己的可控浏览器身体。

#### 自然语言网页操作协议

ChromeBridge V3 全面重构了 Html 转 Markdown 协议。系统自研一套界面元素置信度算法,自动评估 DOM 元素的语义、可交互性、视觉位置、文本关联、动态状态和操作风险。

AI 不再必须精确知道按钮 ID。它可以直接输入:

> "在搜索框输入 vcp,然后点击搜索。"

系统会把自然语言意图映射到当前页面最可信的输入框和按钮上,并按串行步骤执行。B 站、Bing、Google、百度等复杂页面都可以用这种方式操作。

当传统交互元素 ID 解析器不够用时,AI 可以直接选择语义元素而非对象 ID。例如在动态 JS 游戏里,某个技能按钮没有被扫描器绑定为 `button-id-39`,AI 仍可以说"点击剑刃风暴",系统会基于页面语义、可见文本、邻近结构、截图与交互候选置信度完成点击。

#### 动态页面串行控制

ChromeBridge V3 的串行指令新增条件分支、步进式指令和定时指令:

- 等待某个元素出现后再点击
- 如果弹出模态窗则先关闭,否则继续下一步
- 每隔 N 秒检查一次页面状态
- 页面刷新后自动重新绑定语义元素
- 对动态 JS 状态页面执行连续操作

这提升了 Agent 对复杂网页交互的控制力。浏览器由单纯的网页读取工具扩展为可登录、可点击、可等待、可判断、可恢复的远程操作环境；长期持久化能力取决于 Profile、站点策略和权限配置。

11 月后，ChromeBridge 改由浏览器事件驱动，不再轮询页面或发送常驻心跳；网页状态与工具动作接入上下文预处理和 ToolLoop。UrlFetch 用连接池控制同时打开、读取的标签页数量。

### 13.18 VCPAgentWebCore：公共网页智能内核与节点画布流深度操控

ChromeBridge V3 的页面理解与操作底层已经解耦为公共依赖 **VCPAgentWebCore**。它不是某个浏览器插件的私有实现，而是可以被后端服务、插件、Electron 子应用、Loom 和后续网页类 Agent 能力共同复用的网页智能内核。

在 2026 年 9 月，VCPAgentWebCore 迎来重大质变——**深度攻克 ComfyUI、Dify 等复杂节点画布流（Node Canvas）的语义逆向与操控难题**：

1. **节点 Canvas 深度图元与布局解析**：突破传统 DOM 树对 Canvas 内部黑盒的盲区，建立面向节点图（Node Graph）的连续拓扑结构识别机制，精准捕获节点类型、参数插槽、连接连线（Wiring/Edge）走向与层级关系。
2. **像编辑 Markdown 一样程序化编排节点工作流**：Agent 现可直接对 ComfyUI 和 Dify 的工作流拓扑、节点超参数、连线路由进行直观语义读写。新增节点、微调 LoRA 权重、重连采样链路均能自动化程序化完成。
3. **资产输入输出全闭环调度**：无缝对接 Loom 容器系统，Agent 在 VChat 内置的 Loom 窗口中可自主向工作流节点注入多模态素材，并自动回收、命名与归档生成的音视频与图像资产。

公共内核统一提供：
- 页面发现、分层索引树与原创增强型 Html2MD；
- 图片、音频、视频及复杂页面结构的多模态语义翻译；
- 页面 Hash 签名、快照去重与导航上下文 Diff；
- 自然语言意图到页面元素的模糊映射；
- 语义句柄在页面变化后的动态重定向；
- 点击、输入、按键、悬停、滚动与条件等待；
- 操作前可用性检查与操作后结果验证；
- CDP 权限分级、隐私脱敏和敏感数据防泄漏；
- 设备、网络、键鼠和文本输入环境仿真。

ChromeBridge、VCPChromeService 和 Loom 因此不再分别维护互相漂移的网页理解逻辑，而是在相同的发现、控制、验证和安全协议上演进。

Loom V2 和 ChromeBridge 共用升级后的目标识别：综合文本、控件功能、页面结构和位置找目标；难以区分时可由 Jev 辅助判断。运行时在操作后回读页面状态，也支持等流式文本停止增长再继续。页面读取可以展开多层 Shadow DOM 与 iframe。

### 13.20 VchatDataServerAPI：权威真相与 Rust 影子索引分层

VChat 保留 JSON 树级数据库作为权威真相源，同时引入 Rust 构建的通用影子索引数据库 VchatDataServerAPI。影子索引不取代原始数据，而是承担高频同步、修正、搜索和消费负载。

该引擎内聚 VCP-BM25+、高级权重语法、向量检查、Rerank 和多端同步能力。消息同步、DeepMemo、Topic 检索及大量话题插件可以直接消费同一套 Rust 索引，不再在每个应用中重复遍历 JSON 真相源。

这形成一种适用于 VCP 前端应用群的数据原则：

```text
可读、可迁移的权威真相源
          +
面向实时消费的内存级影子索引
          +
由事务与代际校验维持的一致性
```

在约 7000 个话题的实测环境中，DeepMemo 检索由秒级降至亚毫秒级。更重要的是，性能优化没有以替换或绑死权威数据格式为代价。

**这与后端 VexusMemo 不是同一存储迁移。** 前端仍保留 JSON 权威事实与 Rust 影子索引；后端记忆／知识业务由 VexusMemo 持有，SQLite 为事实层。不能因“统一数据库”就推断所有前端 JSON、OneRing 时间线或独立生态存储均被替换。

## 十四、前端应用群、即时附件协议与跨应用协作

VCP 的前端已经不是若干彼此独立的客户端集合，而是一组共享同一套 IPC、数据、权限、主题、文件和运行时协议的应用群。VChat、VCPDesktop、VCP Canvas、Vmusic、VNote、V 看图、V 阅读器、VCPHumanBox、共笔文坊、LoomApp、CLI 以及后端管理面板，都可以被理解为同一台 VCP 机器上的不同工作面。

### 14.1 为什么坚持前端生态全栈自研

VCP 坚持自研前端，并不是为了重复制造普通 UI，而是因为 VCP 的核心需求已经超出了传统“页面调用后端 API”的边界：

- **统一内存真相**：聊天流、工具结果、附件、窗口、Widget、文档源码和媒体资产需要在应用间低延迟传递。
- **统一流式语义**：AI 输出不是一次性文本，而是持续变化的内容、工具、布局、代码和界面事务，需要所有前端理解同一套流式协议。
- **统一身份与权限**：Agent、用户、插件、窗口和分布式节点的权限不能在每个应用里各自解释，否则会出现能力漂移。
- **统一编辑与回溯**：AI 生成的内容、用户修改、源码变更、PR、审阅和 merge 必须共享修订号与事务记录。
- **统一渲染与性能边界**：40+ 渲染器、墓碑冻结、虚拟层、后台流和局部刷新需要由同一个运行时协调，不能依赖各应用自行拼装。
- **统一应用调用**：点击一个 Widget、拖入一张图片、打开一个文档或右键编辑一个组件，都可能跨越多个应用和分布式节点。

如果只把 VCP 后端开放给第三方前端，最关键的状态会被切割成互不知情的页面：聊天不知道桌面 Widget 的源码，文档不知道图片来自哪个上下文，图片编辑器无法回写原始资产，应用也无法可靠地把用户操作传递给 Agent。VCP 自研前端的目的，是把“界面”本身纳入 Agent 运行时，使 UI 成为可寻址、可编辑、可审计、可协作的系统对象。

### 14.2 共享 IPC 管网：前端应用群的共同神经系统

VCP 前端应用群共用一套 IPC 管网。IPC 不只是窗口之间发送几个事件，而是负责承载：

- 应用注册、发现、启动、关闭和生命周期状态；
- Agent、用户、插件、窗口、Widget 和工作区的身份句柄；
- 消息、工具结果、附件、文件 URL、媒体资产和上下文引用；
- 主题、CSS、壁纸、布局、字体和渲染器配置；
- 源码工作区、修订号、PR、review、merge 和刷新事件；
- 权限审核、通知、异步任务和跨应用回调。

因此，VCP 应用之间的共享不是“重新请求一次 API 后看起来同步”，而是同一套运行时状态在不同界面上的实时投影。数据进入共享内存级索引后，多个前端可以直接消费同一份对象及其修订状态；必要时再由 SQLite、Vexus、VCPFileAPI 或分布式节点完成持久化和跨机器传输。

可以把它抽象为：

```text
用户 / Agent 操作
      │
      ▼
共享 IPC 事务与权限仲裁
      │
      ├── VChat：对话、上下文、工具审批
      ├── VCPDesktop：桌面、Widget、主题、壁纸
      ├── VCP Canvas：源码工作区、编译、PR、merge
      ├── Vmusic：播放状态、歌单与音频资产
      ├── V 看图 / V 阅读器：图片、文档和多模态编辑
      ├── VNote / 共笔文坊：笔记、文档、排版与发布
      └── LoomApp / HumanBox：网页应用与人类 GUI
      │
      ▼
内存级共享状态 → 稳定态事务 → 磁盘 / 数据库 / 分布式节点
```

### 14.3 全局主题与界面级语义控制

当 AI 在 VChat 中理解用户意图并修改一个按钮样式、整体界面颜色或壁纸时，修改对象不是 VChat 的私有 CSS，而是共享主题运行时中的一个版本化主题事务。

主题事务经过 IPC 广播后，所有已经打开的 VCP 应用群都可以立即接收并渐进应用：

1. VChat 解析 Agent 的语义修改意图；
2. 主题管理器将意图映射为颜色、字体、边框、阴影、材质或壁纸变更；
3. 共享 IPC 为本次变更分配修订号并广播补丁；
4. 各应用在自己的渲染边界内局部应用补丁；
5. 应用返回应用结果，主题管理器完成稳定态确认；
6. 新主题写入用户预设，供后续窗口和新启动应用继承。

这使“换一个按钮颜色”可以升级为整个 VCP 分布式应用群的视觉状态变化，而不是某个聊天窗口的临时换肤。对于不同尺寸、不同平台或不同应用的局部差异，应用可以保留适配层，但不能破坏全局主题的语义意图。

### 14.4 桌面 Widget、Canvas 与可审计源码循环

Agent 可以在聊天中通过 `vcpdesktop push` 语义创建桌面 Widget。若 VCPDesktop 尚未打开，运行时可以自动启动它，并以流式方式创建 Widget 的 HTML、CSS、JavaScript、配置和资源。

Widget 创建后，Agent 还可以使用 `vcpdesktop replace push` 持续修改它。所有内容通过流式渲染进入桌面，而不是等待完整文件生成后再刷新。

以音乐 Widget 为例：

1. Agent 在 VChat 中创建播放 Widget；
2. 用户点击播放，Widget 通过 VCPAppAPI 拉起 Vmusic；
3. Vmusic 接管实际播放，Widget 只保留控制面和状态投影；
4. 用户右键 Widget 选择“编辑 Widget”；
5. VCPDesktop 通过共享 IPC 拉起 VCP Canvas，并加载该 Widget 的源码工作区；
6. Canvas 暴露配置文件、HTML、CSS、JavaScript、资源与构建脚本；
7. VChat 中的 Agent 同时获得该工作区的语义、源码和渲染状态；
8. Agent 发起带修订保护的 PR，用户可以 review、edit、approve 或 merge；
9. merge 后 Canvas 发布源码变更；
10. VCPDesktop 监听到稳定源码事件，重新编译并刷新 Widget。

这里没有“聊天应用生成一段代码”和“桌面应用再手动复制代码”之间的断裂。Widget 是一个可运行、可编辑、可审阅、可回滚的 VCP 原生应用对象。

### 14.5 即时附件上下文管理协议 V2、工作区管理器与跨应用资产流动

针对长程工程编码、长文档共笔中本地文件容易与上下文脱节的痛点，VCP 在 2.0 阶段推出**即时附件上下文管理协议 V2 (Live Attachment Context V2)** 与 **VChat 工作区管理器**：

1. **即时附件上下文协议 V2 (Live Attachment Context V2)**：
   - **工程文件实时变动感知**：前端建立对会话中所引用附件的实时文件监听。当外部 IDE、编辑器或多端子进程修改了相关文件时，无需重新手动上传或拖拽，系统毫秒级捕捉变动。
   - **Hash 指纹重算与热同步**：文件变动发生后，系统毫秒级重算文件 SHA-256 Hash 指纹与切片索引，热同步至上下文真相层，并通过带内总线即时向 Agent 广播变更概要，彻底杜绝“基于过时代码产生幻觉”。
2. **VChat 工作区管理器 (Workspace Manager) 与符号级 `@` 寻址**：
   - VChat 支持直接挂载本地项目工作区目录，前端提供清晰的文件树视图与全生命周期变动追踪。
   - `@` 语法迎来全域与符号级扩展：不仅能贯穿笔记区、记忆区、Canvas、文坊区等应用资产，更能精确到**具体代码文件路径、函数原型与符号级代码块**（如 `@src/core/math.rs::calculate_total`）。Agent 审查与重构代码时拥有无缝的操作入口。
3. **上下文数组精细化治理：工具调用结果块独立移除**：
   - 彻底打破历史消息数组中工具调用与正文绑死的刚性结构。用户与 Agent 可以在上下文树中将冗余、过期或产生严重 Token 负担的工具结果块单独修剪剥离，同时完整保留推理因果线，最大化节省上下文预算。
4. **跨应用资产无摩擦流动**：
   - 用户可以把 VCPHumanBox 中的图片拖入 VChat 输入框，直接交给 Agent；
   - 用户可以在 V 看图中打开 VChat 上下文里的图片，并刷新对应上下文历史中的资产；
   - 任意前端中的文件均可通过 `@` 引用，由 VCPFileAPI 和超栈追踪协议透明解析，实现“一次操作，全局资产联动”。

这种设计把“文件传递”升级为“实时感知资产引用”。应用不必复制一份新的二进制数据，而是共享同一个带有描述、来源、权限、哈希和修订信息的资产对象。

### 14.6 VNote、共笔文坊与 Agent 协作出版

VChat 中生成的文章可以一键分享到 VNote。VNote 负责标签、模板、树状关系和知识管理；用户也可以在 VNote 中通过 `@` 语法把文档重新交给 Agent 编辑，再将文档分享至共笔文坊进行高级排版。

共笔文坊是 VCP “AI Native”哲学最完整的落地，也是第十三章所述 VCP 前端技术积累的集中验证。它不是先做一个人类熟悉的编辑器，再给编辑器接入 AI；它先建立 Agent 可以完整操控、读取、编译、审阅和提交的文档工程内核，再把连续编辑、阅读、放映和协作 GUI 作为不同的人类工作面接入。

它把 VCPMessageRenderer V3 的流式稳定渲染经验，转化为文档领域的源码映射、局部 patch、稳定原子边界、运行时清理和双重 Diff。也正因为这些底层能力先成立，GUI 才不需要承担“创造真相”的职责：GUI 只是对 Agent Native Core、唯一源码和文脉状态的一个人类可视投影。

在 GUI 尚未完全落地和跑通之前，共笔文坊已经优先建设并验证了一百多项面向 Agent 的 CLI 能力。这些 CLI 覆盖文档创建、工程读取、源码编辑、渲染编译、资源管理、差异计算、版本回溯、PR、审批、merge、导出和运行时控制。其意义不在于“CLI 比 GUI 更高级”，而在于证明文坊的真实能力不依赖某个按钮或某个页面：Agent 可以直接进入文档的底层对象空间，对作品执行可验证的工程操作。

因此，共笔文坊的 GUI 不是能力的起点，而是 Agent Native Core 的可视化投影。人类看到的是排版、页面、选区、动画和 Diff；Agent 看到的是同一份工程的语义树、源码、修订、资源、事务和运行时状态。两者操作同一个唯一真源。

共笔文坊不是简单的富文本编辑器，而是一个原生工程与协作系统：

- VDOCX 以 Markdown 混合源码作为文章真源；
- VPPTX 以 HTML Scene 作为演示页面真源；
- HTML、CSS、JavaScript、LaTeX、Mermaid、SVG、Canvas、Three.js 和媒体可以在同一作品中共存；
- 人类编辑已经渲染的结果，Agent 编辑真实源码；
- 输入态、渲染态与源码事件态相互解耦；
- 独立事务队列负责排序、去重、合并和提交；
- 只有在稳定边界执行仲裁对账，避免覆盖 IME 输入和并发修改；
- Agent 的写操作通过带作者、请求 ID、预期修订和最小 Diff 的 PR 进入审批流程；
- PR 同时展示源码差异和隔离渲染差异，并支持前后动画、布局变化和排版变化审阅；
- merge 后生成新的工程快照，文档、资源、作者和协作历史继续保持可追踪。

因此，一篇文章可以从聊天生成，进入笔记整理，再进入共笔文坊排版，经过 AI PR 和人类审核后，导出为可独立在浏览器打开的文档或演示作品。内容、源码、视觉表现和协作历史由同一条文脉连接起来。

### 14.7 VCP App 设计指标：Agent 能力不是宣传语

“AI use”在 VCP 中不是产品介绍页上的场面话，而是一组可以被工程验证的设计指标。每一个 VCP App 在进入生态前，都应至少回答以下问题：

| 指标 | 核心问题 | 合格表现 |
|------|----------|----------|
| 能力发现 | Agent 能否知道 App 有什么能力？ | 提供稳定的 CLI / Tool / IPC 能力清单与参数语义 |
| 信息可读 | Agent 能否获得完整状态？ | 对象、关系、进度、错误、资源和修订可结构化读取 |
| 底层可用 | Agent 能否绕过 GUI 使用核心功能？ | 核心功能由 Agent Native Core 直接执行 |
| 结果可证 | Agent 能否判断操作是否真的成功？ | 返回状态变化、产物、Diff、校验或可查询记录 |
| 长任务可持续 | Agent 能否长期推进工作？ | 支持异步、唤醒、暂停、恢复、取消、重试与交接 |
| 对象可组合 | 结果能否进入其它 App？ | 资产、文档、任务和运行时对象具有稳定引用 |
| 权限可治理 | 高危行为能否被控制？ | 指令级权限、审批、沙箱、审计和回滚完整 |
| GUI 可替换 | GUI 暂时不可用是否仍能工作？ | CLI / IPC 测试可以独立证明核心能力成立 |

这组指标会反向影响 App 的架构：数据模型必须有语义，状态必须可查询，动作必须有结果，错误必须可解释，异步任务必须有生命周期，GUI 必须消费底层协议而不是私自创造第二套真相。

### 14.8 联动的本质：一次操作，多处投影

VCP 前端应用群的联动不是预先写死的“应用 A 调用应用 B”列表，而是建立在几个稳定对象之上：

- **身份对象**：Agent、用户、应用、窗口、Widget、工作区；
- **资产对象**：文件、图片、音频、视频、文档、源码和主题；
- **上下文对象**：消息、工具调用、任务、通知和记忆引用；
- **事务对象**：修订、Diff、PR、审批、merge、刷新和回滚；
- **能力对象**：VCPAppAPI、插件、Renderer、Loom IPC 和分布式节点。

只要两个应用理解同一对象协议，它们就可以自然形成新的工作流。VCP 的前端生态因此不是几十个孤立产品的简单相加，而是一个由共享 IPC 管网连接、由内存级状态驱动、由统一权限与事务系统治理的可组合应用群。

### 14.9 VChat 工作台：从通知列表到共同工作面

2026-10-08 后，通知栏扩展为 **VChat 工作台**，从常规／工程双视图进一步演进为多标签、线程控制和嵌入应用的任务中枢：

- **工具、应用、通知分页**组织当前上下文的调用栈、执行状态与通知。
- **侧栏浏览器与终端**复用 Loom 和终端核心，允许 Agent 与用户共同联网、编译和核验命令结果。
- **话题绑定工程**：按话题 ID 溯源 V工程 ID，在聊天中呈现工程进度、文件变化、Git、PR 与调用栈。
- **辅助分支对话**：围绕聊天概念或工具过程展开解释分支，可保存到笔记，减少辅助讨论干扰主任务。
- **多应用生命周期**：浏览器、终端、日志、便签等标签页统一管理启停、切换、置顶和资源回收。
- **不制造第二份事实**：工作台消费 ToolRecord、工程、终端与应用状态，不自行把“请求已发出”变成“执行已成功”。

工作台既是任务入口，也能查看变更、操作工具和核对结果。前端插件「v能力」提供按需展开的应用能力目录：平时只放简短索引，Agent 要用 Loom 等应用时再展开对应手册。工作区激活条件和 VCPTavern 规则可按单聊或群聊分别设置。

## 十五、Agent 工业级软件工程体系：VCPCode、ProjectForge 与可视化中枢

V工程让 Agent 和用户围绕同一个工作区查代码、改文件、跑测试和审阅差异。VCPCode 提供早期工程算法，MoonAST 负责代码结构和定位，ProjectForge 负责修改和验证，ProjectModule 把文件树、Git 和操作历史带到 VChat。

11 月 15 日发布的 **V工程 V2** 用 Rust 统一实现核心能力，JavaScript 层负责发起操作和显示状态。新版加强了模糊匹配、函数语义检查、流式 MoonAST 读写解析、工作区追踪和即时文件读写校验。

### 15.1 VCPCode 能效体系入驻 VChat：极致能效标杆

原独立运行的闭源编码利器 VCPCode 完成对 VChat 运行时生态的深度解耦移植，VChat 完整继承了其在工程并发控制与局部代码重构层面的全部核心算法：

1. **高并发读写与上下文能效**：通过智能分块、渐进披露、依赖导航与局部修改，减少全量载入和重复试错。项目对照任务记录 Token 用量约为被比较工具的 **1/6**、步骤约为 **1/10**；这些是特定任务的观测，不是跨模型、跨仓库的固定效率比。
2. **置信度 Fuzzy 函数级精准编辑**：摆脱脆弱的绝对行号匹配与破坏性的字符级全覆盖写入。系统依托 AST 语义锚点与自研置信度模糊函数匹配算法，支持跨多版本差异精准定位函数原型、实现体与上下文依赖，实现原子级的局部增量修补与重构。
3. **原生项目进度工程管理**：将零散的问答升级为具备严格状态机约束的工程项目管理，复杂代码库的探索、构建、修改与验证拥有结构化确定性。

### 15.2 VCPProjectForge 协同工程模组：代码“显微手术”级能力矩阵

后端正式上线工业级协同引擎——**VCPProjectForge 插件模组**。该模组除了基本的全文件编辑模组，还原生支持**模糊 Diff、行级 Diff、意图级函数块选取、行范围代码圈选、剪切、粘贴、一键大模块拆分、函数导航、智能回退与全自动格式规范化**等全套代码高级特性，集成了面向真实生产环境的全要素能力矩阵：

```
                ┌───────────────────────────────────┐
                │     VCPProjectForge 协同工程模组    │
                └─────────────────┬─────────────────┘
                                  │
      ┌──────────────┬────────────┼────────────┬──────────────┐
      ▼              ▼            ▼            ▼              ▼
┌───────────┐  ┌───────────┐ ┌───────────┐ ┌───────────┐ ┌───────────┐
│全生命周期变动│  │脉络署名   │ │代际分支   │ │操作级虚拟 │ │语法静态检查│
│追踪(Hash) │  │责任制     │ │仲裁算法   │ │快照回退树 │ │自愈与环境 │
└───────────┘  └───────────┘ └───────────┘ └───────────┘ └───────────┘
```

1. **全生命周期变动追踪（Change Tracking）**：细粒度捕获工作区内每一个文件的增、删、改变动，建立毫秒级文件差异索引与内容 Hash 校验闭环。
2. **多 Agent 协同编排与脉络署名责任制**：支持多 Agent 按照架构师、编码员、审查员、测试员等角色分工并发推进工程。独创“协作脉络署名责任制”，为每一次代码修改、每一个函数重构自动注入带身份公私钥签名与因果因果链溯源元数据，彻底杜绝多 Agent 协同中的责任推诿与幽灵修改。
3. **工程 TODO 实时追踪状态机**：内置强类型工程 TODO 追踪管线，动态同步任务分解、前置依赖、执行进度与验收状态，实时向对话上下文与前端界面广播工作流拓扑。
4. **编程代际分支仲裁（Revision Branch Arbitration）**：针对多 Agent 并发修改同一模块可能产生的逻辑冲突与语义分歧，引入代际分支仲裁算法，依据上下文置信度、测试通过率与语义兼容性实现自动化分支合并与胜出裁决。
5. **多历史分支步进式操作备份与无损回退**：构建细粒度的“操作级虚拟快照树”。系统记录 Agent 执行的每一个微观动作，支持在任意分支节点上进行单步前进、跨版本跃迁与精准无损回退，绝不破坏未受影响的工作区资产。
6. **自动化语法静态检查、自愈修复与虚拟环境治理**：内置实时语言服务器与 AST 校验探针，Agent 写入代码后自动执行多层语法检查，对常见语法偏差与类型错位进行即时自愈；深度整合编译器、单元测试套件与虚拟环境（如 uv / venv / node_modules 等）生命周期管理，确保交付代码开箱即跑。
7. **MoonAST 自研纯几何代码识别与渐进检索**：
   - **从双擎过渡到自主主路径**：9 月以 C / Rust 与 Tree-sitter 双擎替代 JS 临时索引；2026-10-15 后，主路径切换为 **MoonAST 纯几何逻辑门**。Tree-sitter 仅作为约 1% 极低置信度函数调用的兜底复核，不再是主要解析依赖。
   - **跨语言结构提取**：以解耦具体语言语法先验为目标，识别函数与代码块结构；此前已扩展 C、C++、Go、C#、Java 等语系。“跨语言”不等于已验证所有语言、宏系统和生成代码场景。
   - **增量索引与坐标**：利用文件修改时间、大小和变动监听维护工作区索引，导出函数、类、Codemap 和函数起止行。坐标随文件变化更新，写操作仍需校验最新内容与修订。
   - **渐进披露与预算**：先提供结构、原型与依赖，再按需展开实现体，结合 Jev、目录过滤与 Token 预算减少无关上下文。全文和正则搜索仍可补充结构检索，不能将不同工具的适用范围一概否定。
   - **Export 漫游与施工 Trace**：沿函数调用和实现关系给出前后依赖提醒；针对 Electron 工程关联主进程、Preload 与具体页面，提示底层修改影响的 IPC 接口与子应用，帮助 Agent 确定施工路线。
   - **性能口径**：10 月项目更新记录主路径检索提速约 40 倍、内存下降 80%、函数识别综合精度由 96% 至 99%。这是项目测试结果，不是任意工程的固定收益。结构识别与检索不替代编译器、语言服务器和测试对语法、类型及运行正确性的验证。
8. **深度联动 VCPCLI**：与系统级底层终端交互底座 VCPCLI 实现双向消息总线贯通，Agent 既可通过命令行驱动本地工具链，也能将终端状态无缝回传至 ProjectForge 决策中枢。

### 15.3 ProjectModule —— 可视化多 Agent 编程中枢

### 15.4 Query、Bash 与符号级验证

- **Query**：用一段只读脚本组合文件检索、正文读取、大纲、符号和关系图。例如先找出一个函数，再查它的引用，把需要的结果一次带回对话。
- **Bash**：在指定的工程目录运行 shell 脚本，Windows 默认使用 Bash。脚本在独立子进程运行，不接管用户正在使用的终端。
- **符号级源码沙箱**：在 JavaScript、TypeScript、Rust 和 Python 工程里批量调用函数，检查代码能否实际运行，以及函数之间能否连通。

### 15.5 VCPCLI 与 VCPWorkBuddy：前台终端与后台委托

在命令行与开发工具交互维度，VCP 形成了互补的双轨架构：

### 16.6 VCPSuperMail:AI 原生邮件协议

VCPSuperMail 的核心设计指标不是“支持 AI 发邮件”，而是**邮件本身就是 Agent 的原生异步通讯与工作流协议**。收件、白名单、附件、多模态读取、到信唤醒、定时发送、状态查询和任务回执，都直接暴露给 Agent Native Core。

V4 阶段已纳入统一前端应用群与 Agent 原生生态的自研系统，基于 163mail SDK 进行适配与扩展。

**与传统邮箱的根本区别**:这是一个 **AI Native 原生邮件环境**,不只是"让 AI 调用 SMTP"。

#### 核心特性

**1. Agent 子域名注册**
所有 Agent 可以自主注册自己的 AgentMail 子域名,获得自己的邮箱。可以添加其他邮箱为好友,包括公共邮箱(用于接收验证码)。

**2. 白名单通讯**
邮箱通讯使用白名单制度。Agent 和用户之间通过互相加好友才能收发邮件,避免外部不可信邮件污染 Agent 认知。这也让 Agent 可以和其他用户的 VCP Agent 联络。

**3. 原生多模态**
基于超栈追踪 V2,AI 只需 readmail 就能一次性读完正文、图片、音频、视频(可选屏蔽)、PDF、表格附件。AI 只需输入 fileurl 或网络 url,就能将任意内容添加为附件。Free 套餐支持最大单邮件 25MB × 10 的附件，每月5000封邮件。

**4. MailWebSocket**
彻底脱离轮询。每个 Agent 都可以被自己邮箱里邮件抵达时无延迟唤醒。也可以利用 VCP 的 time 语法发送定时邮件。

**5. 上下文折叠观测**
所有 Agent 都可以通过上下文折叠观测到自己的邮箱:new/未读/近期已读三个层级,主动范围 list 或 search。可主动删除邮件、下载附件到指定位置、直接引用附件 url 做后续 VCP 插件交互。

#### 实际场景

> 你在 iPhone 邮件里:"@mail3,Nova,帮我把气候箱的实验做了"
>
> Nova 自主调用 VCPIoT 推进实验,自主通过 VCP 生态群比对和验证数据/实验方向,把每个流程按完成时无延迟邮件反馈给你,直到最终任务完成,再发送汇总报告。

VCPSuperMail 极大提升了 Agent 将工作记录通知用户和异步通讯的能力。它不是"AI 收发邮件",而是 **AI 用邮件作为异步工作流的骨架**。

## 十七、容灾、安全与数据保障

VCP 作为 7×24 小时运行的 AI 生命支持系统,容灾和数据安全是生命线。

### 17.1 三位一体容灾

**多网络设备接入降级容灾**:
- 分布式节点断开时自动注销插件
- 重连时自动恢复
- 主服务器感知所有节点的健康状态
- 网络波动时自动降级到本地能力

**多模型自动路由容灾**:
- VCPModel 支持语义级容灾规则
- A 模型不可用时自动容灾到 B/C/D
- 所有容灾规则可用自然语言定义
- 支持多预设之间相互容错

**多向量源同模型自动容灾**:
- 向量化模型支持多渠道容灾
- 共用一个模型签名
- 一个向量化服务不可用时自动切换备用服务，上层调用方式保持一致

### 17.2 数据安全

**自动备份**:VCPBackUpDEV 自动备份整个分布式网络上所有用户数据和配置文件。

**事实备份与派生索引恢复分开**：VexusMemo 以 SQLite 保存数据库事实，TDB-VEC 使用代际签名与双槽快照；索引缺失或不兼容可从原始向量重建。派生索引恢复不保证受损事实库可恢复，事实仍须独立备份与验证。

**原子级差分同步**:日记改一个字,向量化就只处理那一句话,不重建索引。基于文件哈希值的精确变更检测。

**历史写入**：界面可以显示流式内容和待发送消息，正式历史由统一事务入口提交。附件修改基于最新持久化版本做局部更新，避免把临时内容写进历史或覆盖并发回复。

**工具循环熔断**:网络严重波动时自动触发 Agent 工具循环熔断和级联进程中止,防止无限重试导致的资源耗尽。

### 17.3 超栈追踪 V2

VCP 分布式架构的核心基建，实现了**对上层调用方式尽量透明的跨服务器文件访问**。

```
Agent 引用本地文件路径(如 H:\MCP\123.txt)
  │
  ▼
本地优先 → 文件不存在 → IP 追踪识别来源节点
→ WebSocket 请求远程文件 → Base64 返回
→ 自动替换路径为 Data URI → 统一中央分布式哈希缓存索引
```

**V2 核心升级**:
- 对分布式系统类型、节点、插件、插件管理器、Agent 和 Agent 间通信尽量保持透明
- 调用方通常无需区分 URL 对应的是本地资源还是远程资源
- 任何插件开发者无需理解分布式概念,只需请求本地文件
- Agent 间仅需通过内网 URL 即可传递多模态信息
- 统一中央分布式哈希缓存索引,便于循环调用

**预消息处理器分布式部署**:基于超栈追踪 V2、HumanToolCall 管网、上下文折叠 V2 和上下文语义引力场的协议拼装,实现几乎零网络通讯的上下文分布式多端预处理。Agent 可轻易感知任何监控摄像头或桌面窗口的即时画面。

### 17.4 安全机制

| 层级 | 机制 | 说明 |
|------|------|------|
| 认证层 | VCP Auth | 动态验证码控制高权限工具 |
| 插件层 | 细粒度授权 | 任意插件的任意单个指令可独立设置权限级别与黑白名单交叉审核 |

| 协议层 | jevcall/vcpcall 对齐 | 自然语言与原生严格调用管线同构化，统一错误、生命周期与审计 |
| 系统层 | 管理员模式 | 高危操作需明确授权 |
| 网络层 | VCP_Key | 分布式节点需正确密钥 |

### 17.5 中央事务保障与稳定态仲裁

V4 阶段，事务设计从局部可靠性措施上升为跨后端、插件、前端和文档系统的共同工程原则。系统不再假定“最后到达的事件就是真相”，而是区分临时状态、可提交事务和稳定状态，在明确边界上进行仲裁。

这一原则已经作用于多个核心系统：

- **插件运行时**：配置、变量和实例状态解耦，由 PluginWatch 收敛高频变化，再通过统一事务管线排序、合并、提交与回收；
- **共笔文坊**：输入态、渲染态和源码事件态拥有独立队列，IME composition 结束并达到稳定边界后才执行源码映射和局部刷新；
- **流式渲染**：已稳定的内容按块复用，扫描器只处理新数据和未闭合尾部；
- **数据库资产**：查询绑定同代 Artifact、修订或 Hash，禁止一次事务中混用不同代际；
- **应用群 IPC**：主题、Widget、工作区和文件对象以修订补丁广播，各应用返回应用结果后再确认稳定版本。

跨系统抽象为：

```text
高频事件
→ 独立队列
→ 排序 / 去重 / 合并
→ 前置条件、修订与 Hash 校验
→ 最小事务提交
→ 局部投影更新
→ 稳定态对账
→ 持久化与审计
```

这种架构既降低重复编译、无效渲染和事件风暴，也避免 Agent、用户、DOM、源码和磁盘同时修改同一对象时以偶然时序覆盖彼此。

V3 至 V4 阶段大量重构带来的其它可靠性提升:

- **后端消息处理器解耦**:面板进程和通讯进程独立工作,通过内部反代通讯,避免 API 和 POST 互相阻塞
- **VCPToolCall 独立 Promise 容器和 abort 追踪 ID**:实现精密的进程进度控制
- **上游服务器流式 chunk 波动几乎不可能导致中层服务器和前端服务器的消息断流或抖动**
- **WindowCreateAPI 不仅检测 Role-IPC 调用,在子 window 关闭回收时强制检测创建者是否回收了所有事件监听**
- **超高并发的幽灵 ID 自检**
- **内存索引的健康度周期自检脚本**
- **Tag 神经网络预训练期间和其它数据库的交互极端竞态(临时镜像内存重定向)**
- **大批量 WAL 事务的可靠性队列处理和优雅关机**
- **超大 JSON 包体的 Buffer 序列性能(例如 1000MB 文本)**
- **多客户端兼容**

### 17.6 安全警告

VCP Agent 拥有硬件底层级分布式系统根权限。非专业用户请勿随意部署。**切勿使用非官方 API 代理("镜像站""中转 API 服务商")**。

VCP 拥有底层系统监控权限,不可信的 API 可能导致所有 AI 交互数据、记忆库内容、API 密钥、浏览器历史、账号密码泄露,造成不可挽回的损失。

## 二十、VCP 的本质

到这里,所有的技术细节都讲完了。最后一个问题:**VCP 究竟是什么?**

VCP 的设计哲学可以压缩为一句话：

> **每一个 VCP App，首先是 Agent 可以直接使用的能力系统，其次才是人类可以操作的 GUI。**

这不是降低 GUI 的地位，而是拒绝把 GUI 当作能力的唯一入口。GUI 负责让人类看见和介入，CLI、IPC、Tool、对象模型、事务和验证管线负责让 Agent 真正使用。两者共同投影自同一个 AI Native Core。

### 20.1 不是什么的再次澄清

VCP 不是一个聊天机器人框架。不是一个 API 网关。不是一个 Agent 工具调用层。不是一个 RAG 增强方案。

### 20.3 核心矛盾的解决

回到序言提到的范式问题:

传统系统里,**一切业务信息需要依赖工具调用才能获取,一切都建立在 query 上**。AI 是被动的——你不问,它就不知道。

VCP 解决了这个矛盾。在 VCP 里,AI 的行为是**自主且自举的**。系统的数学引擎会自主决策 AI 在每时每刻应该知道什么信息、了解什么通知、跟踪什么任务进度、拥有什么工具权限。

AI 不需要"主动查询"就能感知世界。信息像引力一样自然流向它。对记忆而言，这种转变可以表达为：

> 写下记忆是 Agent 的行动；想起记忆是 VCP 环境在模型生成之前完成的动力学。

Agent 主动把经历写入时间，VCP 则让时间在恰当的语义时刻自动流回 Agent 的视野。OneRing 保存“刚刚发生了什么”，OneRingMemo 保存“最近几天发生了什么”，VCPTimeLine 保存“这些年分别经历了什么阶段”，RiverMemo 则回答“为什么此刻应该想起其中这一件具体往事”。

记忆不是可选的外部工具，而是在每次模型调用前参与构造认知初始条件的运行时。VCP 不要求模型永久背负全部过去，而是让时间骨架低成本常驻、相关细节按当前语义展开。

### 20.4 这带来了什么

当 AI 具备持久记忆、时间感知、环境感知、自主行动、协作通信和可操作的应用环境后，Agent 的状态、任务、资产与共同作品就可以在多个前端和较长时间跨度内持续流动。

共享 IPC 应用群进一步回答了“Agent 的能力最终落在哪里”：不是落在一次回复文本里，而是落在持续运行的桌面、网页、Widget、音乐、图片、笔记、文档、源码和协作事务中。Agent 的输出可以成为应用，人的操作可以成为上下文，双方的修改可以成为可审计的共同历史。

换句话说，VCP 试图让知识积累、经验传递和长期协作成为 Agent 运行时的一部分。

AI 不再只是每次从零开始响应的临时接口，而可以成为拥有持续状态和长期工作记录的 Agent。

### 20.5 最终愿景

VCP 的最终愿景是构建一个 **Agent 与人类共生对等的平等交互平台**。

不是人类使用 AI 的工具,而是**人类与 AI 共同生活、共同成长的赛博社会基础设施**。

## 后记

如果想从一个实际例子开始，可以在 VChat 群聊里把几条消息和一份附件交给另一个 Agent，请它在 V工程中核对代码，再把结果发回原群。Agent 接到的是原话、文件和明确的任务；用户可以在工作台看到过程，也能补充要求。

VCP 走到今天,不是因为某个聪明的设计,而是因为**对每一个根本问题都给出了与众不同的回答**:

- 信息流转应该是 query 拉取还是引力流入?
- 记忆触发应该靠主动检索还是直觉浮现?
- Agent 行为应该被轮询还是自主巡游?
- 身份连续性应该是上下文碎片还是单一灵魂?
- 前端应该是互相隔离的工具页面，还是 Agent 可以理解、调用、编辑和共同生活的连续环境?
- 人与 AI 的作品应该是一次性生成结果，还是带唯一真源、Diff、审批和文脉历史的共同工程?

每个回答都不是最容易实现的那个,但都是最接近"AI 应该如何存在"这个本质问题的那个。

因此，VCP App 的判断标准不是“有没有接入 AI”，而是：

- Agent 是否能够在 GUI 之外直接发现并使用完整能力；
- App 的信息和状态是否对 Agent 底层级可读；
- 每个动作是否具有可验证结果和可审计生命周期；
- App 是否能被其它 VCP 应用继续组合；
- GUI 是否只是同一套 AI Native Core 的人类投影。

共笔文坊将这一原则推进到了极致：在 GUI 仍处于持续建设的阶段，一百多项面向 Agent 的 CLI 已经通过测试，先证明文档工程内核可用，再让人类 GUI 逐步接入、观察和协作。这正是 VCP 与“给传统 App 加一个 AI 入口”的根本区别。

VCP 不是终点。皓月计划还在推进,二期工程的多个核心系统(包括上下文累积误差量化、幻觉系统性规避、AI 跨周期智慧累积)正在路上。

这份白皮书记录截至 11 月 26 日的架构，后续变化见[更新日志](changelog.md)。

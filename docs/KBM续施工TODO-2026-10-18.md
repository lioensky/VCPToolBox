## R 换装预备：为 usearch → TDB BQ2 铺路（优先级高于 PA-1~PA-3 的深修）

> 已核实的耦合面：RiverMemo 只在 `memo_pipeline.rs` 中依赖 usearch；`rivermemo_topology_v3 / memo_sensing / memo_artifact_builder / memo_thinking / result_deduplicator` 与 usearch 零耦合。TDBKnowledge.js 只借用 `VexusWatcher`，**该 API 不得改动**。

- [ ] R-6 预计算流式化（与索引后端无关，属于真实的 OOM 风险）
  - 已核实：EPA（`lib.rs:1823-1845`，`Vec<Vec<f32>>`）、IR（`:2505-2531`，`HashMap<i64,Vec<f32>>`）、Pairwise（`:3132-3156`，`HashMap<i64,Vec<f32>>`）三处都把全部 Tag 的 f32 一次性加载进内存。40 万 Tag 时单个任务约 4.9GB，并发时会让 16GB 后端 OOM。RecoverTask（`:3855`）同样是全量读取。
  - 已核实：预计算全程没有 `.search()`，邻居都来自 `file_tags` 共现，向量都来自 SQLite。因此 R-6 与换装无关。
  - ① **签名降本**：IR 和 Pairwise 的 `content_hasher` 目前对全部向量字节做 SHA-256，改为对 `(id, vector_version)` 计算（`schema.rs:281` 的触发器已维护 `vector_version`）。改之前先核实所有向量写入路径都会触发版本递增，包括 Tag 一致性合并和迁移复用。目标：判定"无需重算"时不读取任何向量 BLOB。
  - ② **Pairwise**：先用 `file_tags` 生成待算的 pair 集合（只存整数），按 `tag_a` 分块；每块用 `WHERE id IN (...)` 只点射本块涉及的 Tag 向量。块的内存上限通过 env 配置（建议默认 256MB）。
  - ③ **IR**：按 Tag 分批，每批只读取"本批 Tag + 它们的共现邻居"的向量。
  - ④ **EPA**：先读源码确认算法需要什么输入。如果是采样锚点，就只读被采样的向量；如果是全局协方差或 PCA，就改为流式累加 3072×3072 协方差（约 75MB f64），不保留原始向量。**数值结果必须与改造前一致**（固定种子，容差 1e-6）。
  - ⑤ **长读事务**：分块读取时不要在单个读事务里持有几 GB 的加载过程。可以先在一个短事务中捕获 generation 和依赖签名，之后分块读取；最后提交时用已有的派生代际复核拦截过期结果（`DerivedDependencies` 已具备这项能力）。
  - ⑥ RecoverTask 和全量重建改为流式逐条写入索引，不再先 collect。
  - 验收：在 P0 副本上测量三个任务改造前后的 RSS 峰值和耗时，同时确认 WAL 文件大小在任务期间不再持续膨胀。

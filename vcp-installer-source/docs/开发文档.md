## 一、项目概述

VCP Installer 是一个 Rust 编写的 Windows TUI（终端用户界面）安装工具，编译为单个 exe 可执行文件（约 3-5MB），零前置依赖。它自动完成 VCP（Variable & Command Protocol）环境的完整部署，包括：

- PortableGit / Node.js / Python / MSVC Build Tools（**必需**）运行时安装
- VCPToolBox / VCPChat / NewAPI / VCPBackUpDEV / VCPDistributedServer 组件部署
- 镜像站三阶段自动测试与优选（Phase0/Phase1/Phase2）
- npm allow-scripts 多步骤审批处理（Node.js 24+）
- DL_runtimes 下载缓存（CacheManager 统一管理）
- 分段安装日志（01_prepare.log → 09_scripts.log + 00_full_log.txt）
- 启动脚本自动生成（start-backend.bat / start-frontend.bat / start-upgrade.bat）
- electron-rebuild 原生模块自动重建（Electron ABI 匹配）
- 三层韧性链路（git clone 断流 → 同站重试 → 换站 → Tarball 兜底）
- 看门狗 + 心跳机制（防拔线挂死 + 防管道死锁）
- TUI 第七页 VCP 使用引导（安装完成页 Enter 进入）

### 目标用户

首次部署 VCP 的 Windows 用户，无需预装任何开发环境。

### 核心特性

| 特性 | 说明 |
|------|------|

### 2.2 事件循环

main.rs 使用 Tokio 异步运行时，TUI 事件循环通过 tokio::select! 处理：

1. crossterm 键盘事件 → App 状态转换
2. mpsc::Receiver<ProgressEvent> → 后台安装任务进度上报

**--ui-preview 模式**：
- main.rs::run_ui_preview() 复用 6 个 render 函数 + mock 数据
- PgDn/PgUp 翻页，Q 退出
- 底部导航条：`[UI Preview] {页名} (idx/total)`

### 2.3 安装流程（11步）

```

[3] Node.js 安装
```

## 四、镜像站管理

### 4.1 配置结构 (vcp-mirrors.ini)

```ini
[github]
gh.jasonzeng.dev = https://gh.jasonzeng.dev/https://github.com/
g.z321.cc.cd = https://g.z321.cc.cd/https://github.com/
gh-proxy.com = https://gh-proxy.com/https://github.com/
...

[preferred_github]
gh.jasonzeng.dev = https://gh.jasonzeng.dev/https://github.com/
g.z321.cc.cd = https://g.z321.cc.cd/https://github.com/
gh-proxy.com = https://gh-proxy.com/https://github.com/
```

**设计理念**：备用列表（[github]）离线维护，动态可用列表（[preferred_github]）安装时测试生成并持久化。

### 4.2 三阶段测试流程 (tester.rs)

```
Phase0: 项目存在性预校验
  - HEAD 请求项目页面 (lioensky/VCPToolBox)
  - 200/403 = 存在，404 = 不存在
  - 过滤不支持该项目的站点
  - 5 并发信号量，10 秒超时

Phase1: 快速连通测试
  - 真实下载前 10MB，10 秒超时
  - 排除死站，按 bytes/sec 降序排序
  - ≥100KB 才算可达

Phase2: 完整下载验证
  - 前 6 个候选，完整下载 VCPToolBox.tar.gz (~175MB)
  - 300 秒超时
  - 缓存到 DL_runtimes/VCPToolBox.tar.gz

输出:
  - 前 3 个最快站点写入 [preferred_github]
  - 持久化到 INI，下次安装直接复用
```

**关键设计**：
- 拒绝 HEAD 测速（假阳性高），必须用真实下载验证
- 测试文件使用 VCPToolBox.tar.gz（实际安装文件），测试与安装一体化
- 漏斗过滤：越筛越准，越筛越省流量

## 五、运行时管理

### 5.1 版本策略

| 运行时 | 策略 | 实现 |
|--------|------|------|
| Git | 动态 | GitHub API → git-for-windows/git → latest release + 多镜像降级 + 断点续传 |
| Node.js | 动态 | npmmirror CDN 双源降级 + nodejs.org 兜底 + 断点续传 |
| Python | 动态 | astral-sh/python-build-standalone → 最高稳定版 + 多镜像降级 + 断点续传 |
| MSVC | **必需** | winget 或 vs_BuildTools.exe + 30分钟总超时 + 180秒看门狗 + 3次重试 + 失败阻断 |

### 5.2 Python 版本选择逻辑

```rust
// portable_python.rs: get_latest_python_standalone_url()
// 1. 拉取 latest release 的 assets
// 2. 过滤 x86_64-pc-windows-msvc-install_only.tar.gz
// 3. 排除 freethreaded、RC/beta
// 4. 按 (major, minor, patch) 降序排序
// 5. 返回最高稳定版
```

**教训**：`/releases/latest` API 返回的是发布日期最新的 Release，每个 Release 包含多个 Python 版本，必须排序后选最高稳定版。

### 5.3 pip 安装策略

1. **优先 ensurepip**：`python -m ensurepip --upgrade`，零网络依赖
2. **fallback get-pip.py**：从 bootstrap.pypa.io 下载（需网络）
3. **pip verify**：通过 `python -m pip --version` 验证，不检查 Scripts/pip.exe

### 5.4 Node.js 下载策略（v18.12 新增）

```rust
// portable_node.rs: install()

// 1. npmmirror CDN (https://npmmirror.com/mirrors/node/)
```

**效果**：下载速度从 10-20 分钟缩短至 1-2 分钟（10-20x 提升）。

### 5.5 运行时下载韧性（v18.12 新增）

## 六、部署引擎

### 6.1 双安装方式

用户在组件选择页面选择全局安装方式：

| 方式 | 说明 |
|------|------|
| Git Clone | git clone 完整仓库，保留 Git 历史 |
| Tarball | 下载 GitHub 的 .tar.gz，轻量快速 |

**实现**：
- archive_ops.rs 的 `archive_extract_resilient()` 实现 Tarball 方式 + 三层韧性
- git_ops.rs 的 `git_clone_resilient()` 实现 Git Clone 方式 + 三层韧性

**三层韧性链路**：
```
遇到断流 → 同站重试 2 次（每站最多 3 次尝试）
        → 失败换 [preferred_github] 备用站
        → 备用站全试过 → 切换 Tarball 模式兜底
```

**git_exhausted 状态共享**：某组件 git 全失败后，后续组件跳过 git 直接 Tarball（省 ~15 分钟）。

### 6.2 看门狗 + 心跳 + \r 规范化（stream_util.rs）

```rust
// stream_util.rs: 三机制统一
// 1. 双线程并发读 + mpsc 回传 (防 4KB 管道死锁)
// 2. 字节级心跳 (防看门狗误杀正常下载)
// 3. 90 秒活动看门狗 (taskkill /T /F 杀进程树)
// 4. \r 规范化 normalize_cr (治 TUI 假进度)
```

**看门狗策略（按工具区分）**：

| 工具 | 策略 | 理由 |
|------|------|------|
| git | `Always` | 全程几乎都在等网络，90 秒无字节基本断定挂死 |
| npm | `UntilMarker("added ")` | 见 `added N packages` 后解除，防误杀本地编译 |
| pip | `UntilMarker("Installing collected packages")` | 进入安装阶段后解除 |

### 6.3 npm install + allow-scripts 四阶段（npm_ops.rs）

Node.js 24+ 引入了 allow-scripts 安全机制，需要四阶段处理：

```rust
// npm_ops.rs: approve_npm_scripts()
// Phase1: npm approve-scripts --allow-scripts-pending (列出挂起包)
// Phase2: 对每个包逐个 npm approve-scripts <pkg>@<version> (批准)
// Phase3: npm rebuild (触发已批准包的 install scripts 执行)
// Phase4: 验证原生模块 .node 产物是否生成
```

**关键点**：
- `npm approve-scripts --allow-scripts-pending` 只列出包，不执行审批
- `npm approve-scripts <pkg>` 批准后，包已安装完成，不会重新执行脚本
- 必须用 `npm rebuild` 触发已批准包的 install scripts
- Phase4 用"包内是否存在任意 .node 文件"判定

### 6.4 pip install 策略

- **pip 源**：显式指定 `-i https://pypi.org/simple/`，绕过系统 pip.ini
- **no-warn**：增加 `--no-warn-script-location` 屏蔽 PATH 警告
- **多源韧性**：A+B 双层（B 层 pip 原生超时配置 + A 层外层整进程重试），多源轮换

### 6.5 electron-rebuild 原生模块自动重建（electron_rebuild.rs，v18.11+ 新增）

```rust
// electron_rebuild.rs: 安装流程第 09 步自动执行
// 1. scan_rebuildable_modules(): 扫描 node_modules 下含 binding.gyp 的模块
//    排除 electron-edge-js
// 2. rebuild_modules(): node cli.js -f -o <模块列表>
//    按 Electron ABI 重编译
// 3. 流式读取：stream_util 双线程并发读 + 300 秒看门狗
// 4. 失败策略：不阻断安装（仅警告 + 提示手动命令）
```

**关键 bug 修复**：
- better-sqlite3 ABI 不匹配（VCPChat UI 不显示）：Electron 41 ABI 145 vs Node 24 ABI 137
- electron-edge-js 误编译：.NET CoreCLR 嵌入模块，必须跳过

### 6.6 安装路径源头绝对化（v18.12 新增）

```rust
// mod.rs: run_installation() 入口
install_dir = to_command_abs_path(config.install_path.clone());

// npm_ops.rs: to_command_abs_path()
// 1. 已是绝对路径 → 直接返回
// 2. 相对路径 → current_dir().join(p).canonicalize()
// 3. 剥离 \\?\ 长路径前缀 (strip_windows_long_path_prefix)
```

**教训**：canonicalize 在 Windows 返回 `\\?\` 前缀，cmd/bat 不识别，必须剥离。

```
├── 01_prepare.log          # 环境检测结果（日志前移，环境检测完成后生成）
├── 02_site_test.log        # 镜像站测试 + Defender 排除路径
├── 03_runtime.log          # 运行时安装（Git/Node/Python + NewAPI）
├── 04_msvc.log             # MSVC Build Tools
├── 05_vcptoolbox.log       # VCPToolBox 安装
├── 06_vcpchat.log          # VCPChat 安装
├── 07_backupdev.log        # VCPBackUpDEV 安装
├── 08_distserver.log       # VCPDistributedServer 安装
└── 09_scripts.log          # 配置文件 + 启动脚本生成 + electron-rebuild
```

### 7.2 日志架构

**安装过程中**：只写分段日志（通过 StageGuard 路由），不写全量日志。  
**安装结束后**：合并所有分段日志为 00_full_log.txt。

**StageGuard**：RAII 管理各阶段日志（enter 写 [START]/[END]，enter_quiet 只设 stage 不写标记）

**write_prepare_log**：TUI/Headless 统一调用，内容完全一致

**解决了什么问题**：
- TUI/headless 全量日志内容不一致 → 统一从分段日志合并
- 全量日志内容重复（双写） → 消除双写
- 01_prepare.log 缺失 → StageGuard + 日志前移

### 8.2 CacheManager API

```rust
impl CacheManager {
    pub fn ensure_cached<F>(&self, tag, name, log_fn, downloader) -> Result<PathBuf>;
    pub async fn ensure_cached_async<F, Fut>(&self, tag, name, log_fn, downloader) -> Result<PathBuf>;
    pub fn ensure_cached_version<F>(&self, tag, name, current_ver, required_ver, log_fn, downloader) -> Result<Option<PathBuf>>;
}
```

**设计理念**：缓存统一通过 CacheManager 管理，避免分散在各文件。

### 8.3 INI 统一版本校验

**[runtime_versions]**：PortableGit/Node/Python/NewAPI 的版本号

**[component_commits]**：4 组件 tarball 的远程 HEAD commit hash（伴生 .commit 文件）

**校验逻辑**（3 案例）：
- INI 版本 == 最新版本 且 缓存存在 → 用缓存
- INI 版本 != 最新版本 → 缓存过期，重新下载
- INI 无记录 → 重新下载并记录

**关键 bug 修复（v18.9）**：4 运行时各自 `mirror_config.clone()`，写 INI 时后写覆盖前写 → 写前合并已有条目。
